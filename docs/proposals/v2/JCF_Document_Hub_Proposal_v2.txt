1. Executive Summary
The JCF Document Hub is a native Android application that places the Force's policies, Force Orders, and
Standard Operating Procedures directly in the hands of every serving officer — on duty, off duty, or at home.
Officers authenticate with their existing @jcf.gov.jm webmail credentials and gain immediate, searchable
access to the entire policy library on their personal smartphone.
The application has been designed, built, and tested. It currently indexes 346 documents across 19 categories,
including Force Orders, divisional SOPs, and national policing policies. This proposal recommends a
controlled pilot with a single division, followed by Force-wide rollout under ICTD sponsorship.
Version 2.0 of this proposal expands the original submission to address enterprise security, access control,
API design, secure local storage, offline conflict handling, scalability, DevOps, and legal considerations

2. Background and Problem Statement
Officers across the Jamaica Constabulary Force routinely require access to policy documents to perform their
duties correctly and lawfully. Examples include:
• A patrol officer responding to a missing-person report consulting the Missing Person Investigation
SOP.
• A station commander preparing a disciplinary review consulting the Administrative Review Policy
and SOP.
• A traffic officer requiring the latest Traffic and Mobile Maintenance Division (TMMD) operating
procedures.
• A constable preparing for a promotional examination by studying current Force Orders.
In the current operating environment, accessing these documents typically requires:
• Physical presence at a station with access to the JCF network.
• Requesting copies via email from a supervisor or colleague.
• Reliance on printed binders that risk falling out of date.
• Searching through informal channels (e.g. WhatsApp threads) for forwarded copies.
This friction costs officer time, increases the risk of acting on outdated guidance, and prevents officers from
preparing or studying outside of duty hours. It also poses a security risk: documents circulated informally via
messaging platforms are outside the Force's control and cannot be versioned, recalled, or access-restricted.

4. Authentication via JCF Webmail
The application is gated behind the officer's existing JCF webmail credentials (@jcf.gov.jm). This approach
delivers significant operational and security advantages.

4.1 Authentication Flow
Authentication follows the OAuth 2.0 Authorisation Code flow with PKCE, implemented via the Microsoft
Authentication Library (MSAL) for Android:
1. The officer taps Sign In. The app generates a PKCE code verifier and challenge.
2. MSAL redirects to the Microsoft 365 login endpoint for the JCF tenant.
3. The officer enters their @jcf.gov.jm credentials. Microsoft 365 validates them against Azure Active
Directory. MFA is enforced by Conditional Access policy.
4. On successful authentication, Microsoft issues an authorisation code to the app's registered redirect
URI.
5. The app exchanges the code (plus PKCE verifier) for an access token and refresh token over HTTPS.
6. All subsequent API calls carry the access token in the Authorization: Bearer header. The backend
validates the token against the JCF Microsoft 365 tenant on every request.

5. Access Control Model
This section is new in Version 2.0. It defines how Active Directory security groups map to document
categories, how that mapping is enforced on the backend, and how the model is administered.

5.1 Design Principles
•
•
•

•

Access is deny-by-default. An officer who belongs to no relevant AD group sees no documents.
All access control is enforced server-side on every API request. The client application is never trusted
to self-report the caller's permissions.
Group membership is resolved from the Azure AD token claims at request time. The backend does
not cache group membership beyond a single request cycle unless a short-lived (5-minute) server-side
cache is configured for performance.
A nominated Content Owner (see Section 16) maintains the AD group assignments in consultation
with the relevant division heads.

convention JCF-DocHub-{CATEGORY}. Officers are added to the appropriate groups by the ICTD

5.3 Server-Side Enforcement
On every API request the backend performs the following steps before returning any document data:
7. Extract the Bearer token from the Authorization header.
8. Validate the token signature against the JCF Microsoft 365 JWKS endpoint.
9. Confirm the token has not expired and the audience claim matches the registered application ID.
10. Extract the groups claim from the validated token. If the claim is missing or empty, return HTTP 403
Forbidden.
11. For the requested document or category, look up the required group(s) from the access control
configuration.
12. If the caller's groups claim does not include a required group, return HTTP 403 Forbidden. No
document metadata or content is returned.
13. If authorised, stream the requested document or return the metadata list.
The client application is never trusted to communicate its own permission level. Steps 1–6 execute on every
request, including requests for individual PDF pages.

6. Backend API Specification
This section is new in Version 2.0. It defines the RESTful API surface the mobile application uses to
communicate with the JCF backend. All endpoints require a valid Bearer token and enforce the access control
rules described in Section 5.

6.1 Base URL and Versioning
All endpoints are prefixed with /api/v1/. When a breaking change is required, a new version prefix (e.g.
/api/v2/) is introduced alongside the existing one, giving clients a documented migration window of at least
90 days before the old version is retired.

6.2 Authentication Header
Every request must carry: Authorization: Bearer {access_token}
Requests without a valid token receive HTTP 401 Unauthorised. Requests with a valid token but insufficient
group membership receive HTTP 403 Forbidden.

10. Offline and Caching Strategy
This section is new in Version 2.0. It defines how the application behaves when no data connection is
available and how conflicts between cached and server-side content are resolved.

10.1 What is Cached
Data type

Caching behaviour

Category list

Cached in-memory on app launch. Refreshed from server on each
new session. Not persisted to disk.

Document metadata list

Cached in the local database (Room, encrypted) for 24 hours per
category. Displayed to the officer when offline.

PDF files

Cached to encrypted app-private storage on first open. 7-day TTL.
Maximum 500 MB total.

Sync manifest

Fetched in the background every 6 hours when the device has
connectivity. Used to detect updated documents without requiring a
full re-download.

10.2 Offline Mode Behaviour
•
•
•
•
•

When no connection is available, the app displays an Offline banner in the header.
The officer can browse cached category lists and document metadata.
Documents previously opened are available in full from the encrypted local cache.
Documents not previously opened display a Not available offline notice.
Search operates against the locally cached metadata only; full-text search across PDF content is not
available offline.

10.3 Conflict Resolution
When the app re-connects after a period offline, the following process executes:
14. The app fetches the sync manifest from /api/v1/sync/manifest.
15. For each cached document, the local SHA-256 hash is compared to the hash in the manifest.
16. Documents where the hash differs are marked as Updated on server. The cached copy is immediately
deleted.
17. When the officer next opens the updated document, the current version is fetched from the server.
18. A notification is shown: "X document(s) have been updated. Tap to refresh."
There is no merge or diff operation — policy documents are always authoritative from the server. The
officer's locally cached copy is replaced in full.

the full file to download.

Thumbnail caching

First-page thumbnails are generated once and cached server-side for
24 hours. Regenerated only when the document is updated.

CDN / edge caching

Static document content (PDFs and thumbnails) is served via Azure
CDN. Dynamic API responses (lists, metadata, search) are served
directly from the application server. Cache-Control headers are set
appropriately.

SharePoint throttling

If SharePoint is the document store, the backend implements retry
logic with exponential back-off to handle Microsoft's per-tenant
throttling limits.

13.4 API Versioning Strategy
The API follows URI versioning (/api/v1/, /api/v2/). The versioning policy is:
• Non-breaking changes (adding optional fields, new endpoints) may be made to an existing version
without a version bump.
• Breaking changes (removing fields, changing authentication requirements) require a new version
prefix.
• Old versions are supported for a minimum of 90 days after the new version is published. The sunset
date is communicated via the Deprecation: and Sunset: response headers.
• The mobile app always targets the latest stable API version. Older app versions that target a
deprecated API receive an X-Api-Deprecated: true response header, and the app displays an in-app
upgrade prompt.
