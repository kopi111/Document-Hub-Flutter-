## Worker 01 — repository-logic

## Chat Repository QA Findings

---

### [BUG] `startGroupConversation` — uncopied `members` list stored by reference

**File:** `chat_repository.dart`, `startGroupConversation`, `ChatGroup(... members: members ...)`

The caller's `members` list is stored directly inside `ChatGroup` without a defensive copy. Any stateful widget that holds the selection list and mutates it after calling `startGroupConversation` (e.g., clearing it for a fresh dialog) will silently alter the live group's membership. The seeded group also does this: `members: _groupMembers`.

**Fix:** `members: List.unmodifiable(members)` (or `[...members]`) at both the call in `startGroupConversation` and in the seed `ChatGroup` constructor.

---

### [BUG] `availableContacts` silently excludes seed conversation contacts from the roster

**File:** `chat_repository.dart`, `_conversations` seed, `_roster`

Seeded conversations use contact ids `off-101`–`off-106`; the roster uses `off-201`–`off-206`. The `inThread` set built in `availableContacts()` will contain `off-101`–`off-106`, but those ids never appear in `_roster`, so the filter has no effect on them. The user sees seven existing conversations but can never find those six officers in "New Conversation" — they are unreachable from the roster. This is likely an unintentional split dataset, not a deliberate design.

**Fix:** Either add `off-101`–`off-106` to `_roster`, or give all seed conversation contacts ids drawn from `_roster` (`off-201`–`off-206`).

---

### [RISK] `_groupMembers` aliases `_roster` objects directly

**File:** `chat_repository.dart`, `_groupMembers` definition

```dart
static final List<ChatContact> _groupMembers = [
  _roster[0], _roster[2], _roster[5],
];
```

`_groupMembers[0]` is the same object instance as `_roster[0]`. If `ChatContact` has mutable fields (e.g., `isOnline`, `lastSeen`) and any code path mutates a contact received from `availableContacts()`, that mutation propagates into the seeded group's member list and into the roster simultaneously — invisible aliasing across three data structures.

**Fix:** Copy contacts at the definition site: `_roster[0].copyWith()` (or construct new instances).

---

### [RISK] `startConversation` double-traverses a lazy `where` iterable

**File:** `chat_repository.dart`, `startConversation`

```dart
final existing = _conversations.where(...);
if (existing.isNotEmpty) return existing.first;
```

`where()` returns a lazy `Iterable`. `isNotEmpty` and `first` each traverse `_conversations` from the beginning. In a future refactor where this method becomes truly async (real `await` inserted between the two calls), a concurrent insert could cause the guard and the retrieval to see different list states, returning a stale result or skipping the duplicate check.

**Fix:** `final existing = _conversations.where(...).firstOrNull;` — one traversal, no double-access risk.

---

### [EDGE] `startGroupConversation` has no duplicate-group guard

**File:** `chat_repository.dart`, `startGroupConversation`

Calling `startGroupConversation('Alpha Team', members)` twice in quick succession (e.g., double-tap on a confirm button) inserts two distinct group conversations with different `_groupSequence` ids but identical names and membership. There is no idempotency guard unlike `startConversation`.

**Fix:** Add a pre-check: if `_conversations` already contains a group with the same `name` and identical member id set, return the existing one.

---

### [NIT] `_groupSequence` id computed before vs. after increment is consistent but fragile

**File:** `chat_repository.dart`, `startGroupConversation`

`_groupSequence++` happens before both `ChatGroup(id: 'grp-new-$_groupSequence')` and `officerAvatar('grp-new-$_groupSequence')`. The sequence value used in both is the post-increment value, which is correct. However, the id string is written out twice independently; a future copy-paste to a third use site could accidentally capture a different sequence value.

**Fix:** Extract `final groupId = 'grp-new-$_groupSequence';` immediately after the increment and reference only `groupId`.

---

**TOP ISSUE:** `startGroupConversation` stores the caller's `members` list by reference — a mutating widget can silently corrupt live group membership without any error or notification.

## Worker 02 — thread-screen

## Chat Thread Screen — QA Review

---

### [BUG] `_sendMessage` — keyboard not dismissed after send

**File:** `chat_thread_screen.dart`, `_sendMessage()`

`_inputController.clear()` is called but `FocusScope.of(context).unfocus()` (or `FocusManager.instance.primaryFocus?.unfocus()`) is never called. On mobile, the software keyboard stays open after tapping the send button, which shifts the viewport and partially obscures the newly added message even after `_scrollToBottom()` runs. The `addPostFrameCallback` scroll fires *before* the keyboard animates away, so `maxScrollExtent` is computed against the keyboard-visible layout and the list undershoots.

**Fix:** Call `FocusScope.of(context).unfocus()` at the top of `_sendMessage()` (before the `setState`), or at minimum before scheduling `_scrollToBottom()`.

---

### [BUG] `_nextReply()` uses stale count — canned reply is off-by-one

**File:** `chat_thread_screen.dart`, `_scheduleAutoReply()` / `_nextReply()`

`_nextReply()` counts `_messages.where((m) => !m.fromMe).length` at the moment the `Timer` fires (1 600 ms later). By then `_markMyMessagesRead()` has not added the new reply yet, but another `_sendMessage()` call could have fired in that window, changing the outgoing count. More critically, `_nextReplier()` and `_nextReply()` are called at *different times*: `_nextReplier()` is called in `_scheduleAutoReply()` (immediately), while `_nextReply()` is called inside the timer callback. If the user sends another message during the 1.6 s window the reply index shifts, so the name shown in the typing indicator can mismatch the name attached to the reply message.

**Fix:** Capture both `_nextReplier()` and `_nextReply()` in local variables at the start of `_scheduleAutoReply()` and close over them in the `Timer` callback.

---

### [RISK] Mutating `_messages` list directly — no `setState` wrapping the inner loop

**File:** `chat_thread_screen.dart`, `_markMyMessagesRead()`, lines inside `_scheduleAutoReply`'s `setState`

`_markMyMessagesRead()` replaces list elements with `_messages[i] = ...`, which is correct because it runs *inside* the outer `setState`. However, `_messages` is a direct reference to `widget.conversation.messages` — a list owned by a model object shared with other widgets (e.g., the conversation list screen). Mutating it directly means any other widget holding a reference gets the mutation without notification, breaking read-only consumers and making the in-memory model mutable from multiple call sites.

**Fix:** Keep a local defensive copy in `initState` (`_messages = List.of(widget.conversation.messages)`) and push changes back to the model through a method, or make `_messages` a local `late List<ChatMessage>` that is not a live alias.

---

### [RISK] `_scrollToBottom()` called from inside `Timer` callback without `mounted` re-check after `setState`

**File:** `chat_thread_screen.dart`, `_scheduleAutoReply()` ~line 82

The timer callback already checks `if (!mounted) return` before the outer `setState`, which is correct. But `WidgetsBinding.instance.addPostFrameCallback((_) => _scrollToBottom())` is registered *after* `setState`. If the widget is disposed between the `setState` call completing and the next frame render, `_scrollController` will have been disposed and `_scrollController.hasClients` will throw or return false. The existing `hasClients` guard in `_scrollToBottom()` protects against the throw, but the post-frame callback itself is never cancelled and runs against a dead controller.

**Fix:** Wrap the lambda: `addPostFrameCallback((_) { if (mounted) _scrollToBottom(); })`. Apply consistently to all three `addPostFrameCallback` call sites.

---

### [EDGE] `onSubmitted` on multiline `TextField` fires on every newline

**File:** `chat_thread_screen.dart`, `_MessageInputRow.build()`, the `TextField`

`keyboardType: TextInputType.multiline` with `maxLines: null` is correct for a multiline composer, but `onSubmitted: (_) => onSend()` will fire every time the user presses the Enter/Return key on a hardware keyboard (including soft-keyboard return on some Android keyboards). This sends the message mid-composition instead of inserting a newline, defeating the multiline setting.

**Fix:** Remove `onSubmitted` from this `TextField`, or use `onSubmitted` only when `keyboardType` is single-line. Handle send exclusively through the button.

---

### [EDGE] `_StatusTicks` shows `Icons.check_rounded` for `MessageStatus.sent` but no icon for `MessageStatus.delivered`

**File:** `chat_thread_screen.dart`, `_StatusTicks.build()`

`icon` is set to `Icons.check_rounded` when `status == MessageStatus.sent`, and `Icons.done_all_rounded` otherwise. If `MessageStatus` has a `delivered` variant, it will silently render `done_all_rounded` (double tick) even though the message hasn't been read, making delivered and read visually identical. Only the colour distinguishes read (blue) vs. not-read (grey).

**Fix:** Add an explicit `switch` or `if/else if` covering every `MessageStatus` variant so new statuses don't accidentally merge with an existing bucket.

---

### [EDGE] `_shouldShowTimestamp()` compares wall-clock `sentAt` values that are both `DateTime.now()`

**File:** `chat_thread_screen.dart`, `_MessageBubble._shouldShowTimestamp()`

The outgoing message and the auto-reply are both stamped with `DateTime.now()` approximately 1 600 ms apart. In fast-send scenarios (user taps send multiple times), consecutive messages will share nearly identical timestamps. The `>= 10` minute threshold is high, so this is benign for normal use, but if the threshold were ever lowered the gap calculation would still be correct. No real defect — noted only because the IDs also use `millisecondsSinceEpoch` with no collision guard (see below).

---

### [NIT] Message ID collision under rapid send

**File:** `chat_thread_screen.dart`, `_sendMessage()` line ~58

`id: 'msg-sent-${DateTime.now().millisecondsSinceEpoch}'` is not unique if the user taps send twice within the same millisecond (possible on fast devices). Similarly for the reply id in `_scheduleAutoReply`.

**Fix:** Use a monotonic counter (`static int _idSeq = 0; id: 'msg-${++_idSeq}'`) or `UniqueKey().toString()`.

---

**TOP ISSUE:** `onSubmitted: (_) => onSend()` on a multiline `TextField` — pressing Enter sends instead of inserting a newline, making the multiline input effectively broken on hardware keyboards and some soft keyboards.

## Worker 03 — list-screen

## Chat List Screen — QA Findings

---

### [BUG] `_loadConversations` resets `_loading = true` only on first call

**File:** `chat_list_screen.dart`, `_loadConversations()`

`_loading` is initialized to `true` but never reset to `true` at the top of `_loadConversations`. On subsequent calls (after returning from a thread, or after creating a chat), the list rebuilds from stale `_conversations` data while the `await` is in flight — there is no loading indicator on refresh, so if the fetch takes time the user sees an outdated list without any feedback. Worse, if the fetch throws on a refresh, `_error` is set but `_conversations` is not cleared, leaving the error state and the old data inconsistent (only the error string is shown, but the model is stale).

**Fix:** Add `setState(() { _loading = true; _error = null; });` at the top of `_loadConversations` before the `await`.

---

### [BUG] `_startNewConversation` calls `_openThread` after `_loadConversations`, causing a double-load

**File:** `chat_list_screen.dart`, `_startNewConversation()` lines ~65–80

The flow is: `_loadConversations()` → `_openThread(conversation)` → which itself calls `_loadConversations()` again on return. This means after creating a chat and then closing the thread, conversations are fetched twice in sequence. More critically, if `_loadConversations` throws the second time (inside `_openThread`'s return path), the error is silently swallowed because there is no handling there separate from the first call.

**Fix:** Remove the `await _loadConversations()` call before `_openThread` in `_startNewConversation`; let `_openThread`'s own post-pop reload handle it, or reload only once after the thread closes.

---

### [EDGE] Pull-to-refresh is unreachable when `_conversations` is empty

**File:** `chat_list_screen.dart`, `_buildBody()`

The `RefreshIndicator` wraps the `ListView` but is only rendered when `_conversations.isNotEmpty`. If the first load returns an empty list or if all conversations are later deleted, the user cannot pull-to-refresh to retry or check for new conversations — they're stuck on the static "No conversations" text with no escape except the FAB.

**Fix:** Wrap the empty-state `Center` widget in a `RefreshIndicator` as well, or use a `CustomScrollView` + `SliverFillRemaining` so the `RefreshIndicator` covers all states.

---

### [EDGE] Error state also lacks pull-to-refresh

**File:** `chat_list_screen.dart`, `_buildBody()`

Same structural problem as the empty state: the error `Center` is returned outside any `RefreshIndicator`. A user who hits a transient network error has no way to retry without leaving and re-entering the screen (the FAB will re-trigger `_startNewConversation`, not a plain reload).

**Fix:** Wrap the error `Center` in a `RefreshIndicator(onRefresh: _loadConversations, ...)`, or add a "Retry" `TextButton` alongside the error text.

---

### [EDGE] `_formatTime` uses local 24-hour time without date context

**File:** `chat_list_screen.dart`, `_ConversationTile._formatTime()`

`sentAt.hour` / `sentAt.minute` are local time, which is correct, but the format shows only `HH:mm` regardless of whether the message was sent today, yesterday, or a week ago. A conversation from three days ago shows `14:32` the same as one from five minutes ago.

**Fix:** Compare `sentAt.toLocal().date` against `DateTime.now().toLocal().date`; show `HH:mm` for today, `Yesterday` for yesterday, and `dd/MM` for older messages (standard messaging app convention).

---

### [NIT] `separatorBuilder` uses a Dart 3 wildcard parameter (`_`) on both positional args

**File:** `chat_list_screen.dart`, `ListView.separated` ~line 110

```dart
separatorBuilder: (_, _) => Divider(...)
```

The double `_` wildcard requires Dart 3.7+. If the project targets an earlier SDK this is a compile error. Using `(_, __)` is compatible with all Dart 3.x versions.

**Fix:** Change to `(_, __) => Divider(...)`.

---

**TOP ISSUE:** `_loadConversations` never sets `_loading = true` on re-entry, so refreshes are invisible and a failed refresh leaves `_error` set while `_conversations` retains stale data — the screen state becomes internally inconsistent on any post-navigation reload.

## Worker 04 — new-chat-and-group

## Chat / Group Creation – QA Review

---

### `new_group_screen.dart`

**[BUG] `separatorBuilder` uses a wildcard `_` for both parameters — Dart syntax error**
```dart
separatorBuilder: (_, _) => Divider(...)
```
Two positional parameters named `_` is illegal in Dart; the second `_` is a redefinition in the same scope. This will not compile.
Fix: `separatorBuilder: (_, __) => Divider(...)`

---

**[EDGE] `_canCreate` allows exactly 1 member when contact list has only 1 entry**
The guard `_selectedIds.length >= 2` is correct, but the empty-contacts path in `_buildContactList` shows "No officers available to add." while still allowing navigation to `NewGroupScreen` from `NewChatScreen`. If the repository returns exactly one contact, the user sees a list of one, cannot satisfy the >= 2 requirement, and is silently stuck with no explanation tied to the disabled Create button.
Fix: Show a dedicated message ("Need at least two officers to create a group") when `_contacts.length < 2` instead of falling through to a single-item list with a permanently disabled button.

---

**[EDGE] `_toggle` operates on `_selectedIds` by contact ID, but `_contacts` list is never refreshed — stale IDs can persist**
If `availableContacts()` could return a different set on retry (e.g. after a failed `_create` → user navigates back → error path), IDs in `_selectedIds` that no longer exist in `_contacts` are silently included in the `members` list filter, but produce an empty match and inflate `_selectedIds.length` without a visible tile, making `_canCreate` true with fewer visible members than expected.
Fix: Clear `_selectedIds` whenever `_contacts` is reloaded, or validate that every selected ID still exists in `_contacts` before computing `_canCreate`.

---

**[EDGE] No maximum group name length or member cap enforced**
`TextField` has no `maxLength` and `startGroupConversation` receives an unbounded `members` list. Depending on downstream repository behaviour this may cause UI/layout overflow in the conversation list or silent truncation.
Fix: Add `maxLength: 40` (or whatever the repository/UI design supports) to the `TextField` and document or enforce a member ceiling.

---

**[RISK] `_create` does not reset `_creating = false` on a clean success path before `pop`**
This is harmless in normal flow (the widget is disposed immediately), but if the `pop` fails silently for any reason (e.g. navigator already popped), the button stays permanently disabled with no user feedback.
Fix: Wrap the success `pop` in the same try block and always reset `_creating` in a `finally` clause.

---

**[NIT] `_buildSelectionCount` hint copy says "two members" but `_canCreate` counts selected contacts only — the creating officer is implicitly the third participant but is never mentioned**
If the current officer is auto-added by the repository, a group of "two members" is actually three participants total. The hint copy should align with what the user will actually see in the conversation.

---

### `new_chat_screen.dart`

**[EDGE] `availableContacts()` is called independently in both `NewChatScreen` and `NewGroupScreen` — no deduplication across the two loads**
When the user taps "New group", a second `availableContacts()` call fires inside `NewGroupScreen.initState`. If the repository is async and eventually consistent, the two calls may return different snapshots, so a contact that appeared in the 1-to-1 list might be absent (or extra) in the group picker.
Fix: Pass the already-loaded contacts list from `NewChatScreen` into `NewGroupScreen` as a constructor parameter, or use a shared cache in the repository.

---

**[EDGE] Tapping a `_ContactTile` while `_createGroup` navigation is in flight is possible**
`_createGroup` is `async` and there is no `_loading`-style guard. A fast double-tap on "New group" can push `NewGroupScreen` twice.
Fix: Add a `bool _navigating` flag, set it before `Navigator.push`, and clear it in the `finally`/callback, then gate `_createGroup` on `!_navigating`.

---

**[NIT] `_NewGroupTile.onTap` is typed `VoidCallback`, not `Future<void> Function()`, so any `async` exception from `_createGroup` is silently swallowed**
This is cosmetic in current code but misleading if the callback signature is ever reused. Consider `GestureTapCallback` or just leave as-is with a code comment.

---

**TOP ISSUE:** The `separatorBuilder: (_, _)` duplicate-parameter syntax error in `new_group_screen.dart` is a compile-time failure that prevents the entire chat feature from building.

## Worker 05 — model-message

## `lib/models/chat/chat_message.dart` — Review Findings

---

**[BUG] No `copyWith` method**

The class is `const`/immutable but provides no mutation helper. The UI will need to update `status` as delivery receipts arrive (sent → delivered → read). Without `copyWith`, callers will reconstruct the object manually, risking forgetting fields and introducing bugs.

```dart
ChatMessage copyWith({MessageStatus? status, ...}) =>
    ChatMessage(id: id, text: text, sentAt: sentAt, fromMe: fromMe,
                status: status ?? this.status, senderName: senderName);
```

---

**[BUG] No `==` / `hashCode` override**

Without these, list diffing (e.g. `ListView` with a `ValueKey`, or `setState` change detection) falls back to reference equality. Two `ChatMessage` objects with identical fields will be treated as different, causing unnecessary rebuilds or failed deduplication.

```dart
@override
bool operator ==(Object other) =>
    other is ChatMessage && other.id == id && other.status == status;

@override
int get hashCode => Object.hash(id, status);
```

---

**[RISK] `sentAt` uses local `DateTime`, not UTC**

`DateTime.now()` produces device-local time. If messages are ever persisted or compared across devices (even in a future backend migration), timestamps will be inconsistent. Callers should use `DateTime.now().toUtc()`, or the field should be documented as "must be UTC" with a factory enforcing it.

*Fix:* Assert or convert: `assert(!sentAt.isUtc == false, 'sentAt must be UTC');` or accept only UTC in a named constructor.

---

**[RISK] `status` default is `MessageStatus.sent` for all messages, including inbound**

The doc-comment says inbound messages "always read as delivered", but the default is `sent`. A caller constructing an inbound message (`fromMe: false`) who omits `status` gets `sent`, not `delivered`. The model should enforce this invariant rather than relying on every call-site to remember it.

*Fix:* Use a factory or add an assertion:
```dart
assert(fromMe || status == MessageStatus.delivered,
    'Inbound messages must use status: MessageStatus.delivered');
```

---

**[EDGE] Missing `mediaUrl` / attachment field**

Chat UIs almost universally gain image/file sharing. Adding it now as `final String? mediaUrl` costs nothing and avoids a breaking model change later. Not a bug today, but a predictable gap once the UI evolves.

---

**[NIT] `id` type is `String` with no format contract**

If `id` is a UUID, say so. If it's a sequential int cast to String, that matters for sort order. An undocumented `id` type makes deduplication logic fragile.

*Fix:* One-line comment: `/// UUID v4, unique per message across all threads.`

---

**TOP ISSUE:** The absence of `==`/`hashCode` is the most dangerous gap — it silently breaks list diffing and any `Set`-based deduplication, causing subtle UI bugs that are hard to trace.

## Worker 06 — model-conversation

## `ChatConversation` — Conversation Model QA

---

### Findings

**[BUG] `messages` is an exposed, mutable `List` — `_seenInbound` silently desynchronises**
`chat_conversation.dart` — field `messages`, getter `unreadCount`

`final List<ChatMessage> messages` makes the *reference* final but leaves the list contents open to mutation. Any caller can call `conversation.messages.remove(msg)` or `messages.clear()`. After `markRead()` sets `_seenInbound = _inboundCount`, removing inbound messages makes `_inboundCount < _seenInbound`; the `unread < 0 ? 0 : unread` guard clamps to `0` — permanently. New inbound messages added *after* the removal are then silently swallowed: `unreadCount` stays `0` even though the officer has never seen them.
**Fix:** In the constructor assign `this.messages = List.unmodifiable(messages)` (change the field type to `List<ChatMessage>`), and expose an explicit `ChatConversation copyWithNewMessage(ChatMessage m)` factory.

---

**[RISK] `_seenInbound` mixed into an otherwise final-field struct**
`chat_conversation.dart` — field `_seenInbound`, method `markRead()`

All public fields are `final`, giving the class the appearance of an immutable value object. The mutable `_seenInbound` breaks that contract: if the app ever copies or rebuilds `ChatConversation` (e.g., for `setState`, a `copyWith`, or a list replace), the new instance starts with `_seenInbound = 0`, resetting the "already read" count and producing phantom unread badges.
**Fix:** Either commit to full mutability (document it, add a `ValueNotifier` / `ChangeNotifier`), or lift read-state out into a separate `ConversationReadState` that lives in the view-model.

---

**[EDGE] `lastMessage` sentinel uses `DateTime(2000)` — corrupts time-based conversation ordering**
`chat_conversation.dart` — `lastMessage` getter, `DateTime(2000)`

If the conversation list is sorted by `lastMessage.sentAt` (the natural display sort), empty threads get a concrete year-2000 timestamp rather than a "no date" sentinel. They will sort *before* every real conversation in ascending order, making empty threads appear at the top on first launch.
**Fix:** Use `DateTime.fromMillisecondsSinceEpoch(0)` for clarity, **or** change the return type to `ChatMessage?` and let callers handle the null — it makes the "no messages" state explicit.

---

**[EDGE] No constructor-level enforcement of the group/contact invariant**
`chat_conversation.dart` — constructor, class doc

The doc comment promises "for a group it holds a representative member so name/rank/station are never blank", but nothing in the constructor validates this. A `ChatConversation` whose `group != null` and whose `contact` is a blank placeholder will silently produce empty strings in `subtitle` and `avatarInitials` once the `??` chain falls through to the uninitialized contact.
**Fix:** Add an assertion: `assert(!isGroup || contact.name.isNotEmpty, 'Group conversations require a valid representative contact')`.

---

**[NIT] Sentinel `id: ''` in `lastMessage` could cause deduplication/equality bugs downstream**
`chat_conversation.dart` — `lastMessage` getter

If any downstream code uses `lastMessage.id` as a map key, deduplicates messages, or compares IDs, two separate empty-conversation sentinels with `id: ''` would collide.
**Fix:** Use a private static `const _emptySentinel` or a well-known constant string like `'__empty__'` to make the intent explicit and avoid accidental equality.

---

**TOP ISSUE:** The publicly mutable `messages` list allows any caller to remove inbound messages after `markRead()`, permanently clamping `unreadCount` to `0` and hiding new unread messages from the officer.

## Worker 07 — model-contact-group

## Chat Model Review — Contact & Group Slice

---

### `lib/models/chat/chat_contact.dart`

**[BUG] `initials` — single-character name crashes with `RangeError`**
`parts.first.substring(0, 1)` is safe, but the multi-word branch uses `parts.first[0]` / `parts.last[0]` without length checks. If a whitespace-only token somehow survives the split (e.g. a name with a trailing non-breaking space that `\s+` doesn't consume on all platforms), `parts.last` could be an empty string and `[0]` throws.
*Fix:* `parts.first.isNotEmpty ? parts.first[0] : '?'` for each side, or filter empty parts after split: `parts.where((p) => p.isNotEmpty).toList()`.

**[EDGE] `initials` — single-word name uses `substring(0,1)` but multi-word uses direct index `[0]`**
Inconsistent access style; one path uses `substring`, the other uses operator `[]`. Both are fine for non-empty strings, but the inconsistency will cause confusion when the next developer edits only one branch.
*Fix:* Use `parts.first[0]` everywhere (after the empty-part filter above).

**[EDGE] `lastSeen` semantic gap — online + non-null `lastSeen` is silently ignored but never validated**
The doc comment says "ignored while `isOnline` is true", but there is no constructor-level assertion or factory validation. A caller can pass `isOnline: true, lastSeen: someDateTime` and the object is inconsistent. In an in-memory model this leaks into display code that must defensively re-check `isOnline` rather than trusting `lastSeen == null` as the online indicator.
*Fix:* Add `assert(!isOnline || lastSeen == null, 'lastSeen should be null while officer is online')` in the constructor body, or document that consumers must check `isOnline` first before reading `lastSeen`.

**[NIT] `const` constructor with mutable semantics risk**
`lastSeen` is `DateTime?` — `DateTime` is itself immutable, so `const` is fine here. No action needed, but worth noting that adding any `List` field later will silently break `const`-ness.

---

### `lib/models/chat/chat_group.dart`

**[BUG] `members` list is mutable — `const` constructor does not enforce immutability**

## Worker 11 — presence

## Presence / Last-seen Logic — Review Findings

---

### [BUG] `_relativeFromNow` — future-dated timestamps silently show "just now"
**File:** `lib/screens/chat/chat_presence.dart`, line 23–28 (`_relativeFromNow`)

`DateTime.now().difference(moment)` returns a **negative** `Duration` when `moment` is in the future (clock skew between devices, or a bad write path). In Dart, `Duration.inMinutes` on a negative duration is also negative, so `-300 < 1` is `true` — the very first branch fires and returns `'just now'` for a timestamp that is actually *hours in the future*. A user whose `lastSeen` is stamped 2 days ahead of the viewer's clock appears permanently "Last seen just now".

**Fix:** Add a negative-diff guard at the top of the function:
```dart
if (diff.isNegative) return 'just now'; // clock skew — treat as recent
```
Or clamp: `final diff = DateTime.now().difference(moment).abs();` if you want to treat future timestamps as zero distance. Either is safer than the current silent misclassification.

---

### [RISK] `DateTime.now()` vs UTC `lastSeen` — implicit kind-mixing
**File:** `lib/screens/chat/chat_presence.dart`, line 24

`DateTime.now()` produces a **local-time** `DateTime`; `lastSeen` stored from a server payload is almost certainly UTC. Dart's `difference()` uses `millisecondsSinceEpoch` internally, so the arithmetic is correct *today* — but if `lastSeen` is ever constructed with `DateTime(year, month, day, ...)` (no timezone), Dart treats it as local, and the diff silently gains or loses the UTC offset.

**Fix:** Normalise at the call site: `DateTime.now().toUtc().difference(moment.toUtc())`.

---

### [EDGE] "Last seen just now" — awkward label for sub-minute offline contacts
**File:** `lib/screens/chat/chat_presence.dart`, lines 13–14 + 25

When a contact just went offline (< 60 s ago), `presenceLabel` returns `"Last seen just now"`. The phrase reads oddly — most messaging apps show `"Last seen just now"` only for the *last-seen* path, but some apps collapse this into `"Online"` or `"Active just now"` for very short gaps.

More importantly, from a logic standpoint `diff.inMinutes < 1` covers the range 0–59 s, so a contact offline for 59 seconds and one offline for 1 second get the same label. Not technically wrong, but the intent ("recently offline") is indistinguishable from truly-online.

**Fix:** Either surface the sub-minute offline state as `'Active recently'`, or keep it but confirm the UX decision is intentional.

---

### [NIT] No upper bound on day display — shows raw "Nd ago" for stale records
**File:** `lib/screens/chat/chat_presence.dart`, line 28

The final branch returns `'${diff.inDays}d ago'` with no cap. A contact last seen 400 days ago shows `"Last seen 400d ago"`. For an officer app where records may accumulate, a formatted date (`'Last seen 12 Mar'`) would be more readable beyond ~7 days.

**Fix:** Add a branch before the `inDays` return:
```dart
if (diff.inDays >= 7) return DateFormat('d MMM').format(moment);
```

---

**TOP ISSUE:** The negative-`Duration` bug — future-dated `lastSeen` timestamps all silently collapse to "just now", masking clock-skew data corruption with a plausible-looking label.

On re-entering the thread the sent message shows a single grey tick (sent, no reply) with no explanation. `_isContactTyping` was also set `true` before dispose — that state is gone, so the contact appears never to have been typing.

**Fix:** On dispose, if `_replyTimer` is active, fire the reply synchronously (immediate `setState` equivalent on the shared `messages` list) before cancelling the timer.

### [NIT] `chat_list_screen.dart` — double `_loadConversations` call in group-creation path

**Location:** `_ChatListScreenState._startNewConversation` (~line 75)

**Problem:** When a `ChatConversation` is returned (new group), the code calls `await _loadConversations()` and then `await _openThread(conversation)`, which itself calls `await _loadConversations()` again on pop. This triggers two unnecessary state rebuilds for the same data.
