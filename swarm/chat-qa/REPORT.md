## Worker 01 — repository-logic

## Chat Repository QA — Conversation/Group Data Logic

---

### [BUG] `conversations()` — mutable list exposed directly

**File:** `chat_repository.dart`, `InMemoryChatRepository.conversations()`

```dart
Future<List<ChatConversation>> conversations() async => _conversations;
```

Returns the live, mutable static list by reference. Any caller can call `.add()`, `.remove()`, or `.insert()` on the returned value, bypassing `startConversation`/`startGroupConversation` entirely (no ID generation, no dedupe, no `insert(0,...)` ordering). Also means two callers hold the *same* object, so a sort or filter on one silently reorders the other's view.

**Fix:** return `List.unmodifiable(_conversations)` (or `List.from(_conversations)` if a snapshot is preferred).

---

### [RISK] Seeded group's `members` list is mutable; new groups are not

**File:** `chat_repository.dart`, static `_conversations` initializer (~line 130)

```dart
group: ChatGroup(
  id: 'grp-901',
  members: _groupMembers,         // ← bare mutable list
  ...
),
```

`startGroupConversation` correctly wraps caller-supplied members with `List<ChatContact>.unmodifiable(members)`, but the seed group passes `_groupMembers` (a `static final List`) directly. Any code that does `conversation.group.members.add(...)` will silently mutate the shared seed list and affect any other object that holds a reference to `_groupMembers`.

**Fix:** wrap with `List<ChatContact>.unmodifiable(_groupMembers)` in the seed initializer, matching the pattern used in `startGroupConversation`.

---

### [EDGE] `startConversation` — re-accessing an existing thread doesn't move it to front

**File:** `chat_repository.dart`, `startConversation()` (~line 52)

```dart
if (existing.isNotEmpty) return existing.first;
```

New conversations are `insert(0, …)` (top of list). But if the user opens an existing conversation, it is returned at its current position with no re-sort. Callers that rely on the list being in recency order will silently see a stale ordering after re-entry.

**Fix:** on the early-return path, move the found conversation to index 0: `_conversations.remove(found); _conversations.insert(0, found);`.

---

### [EDGE] `startGroupConversation` — allows a "group" of one member

**File:** `chat_repository.dart`, `startGroupConversation()` (~line 64)

```dart
if (members.isEmpty) {
  throw ArgumentError('A group conversation needs at least one member.');
}
```

The guard accepts `members.length == 1`, while the error message implies 1 is valid. A single-member group is semantically indistinguishable from a 1:1 thread and will not be filtered by `availableContacts()` (which skips groups), creating a ghost entry.

**Fix:** change condition to `members.length < 2` and update the message to `'A group conversation needs at least two members.'`

---

### [RISK] All state is `static` — no isolation between instances or tests

**File:** `chat_repository.dart`, `_conversations`, `_roster`, `_groupMembers`, `_groupSequence`

The class comment notes this is intentional for session persistence, but the consequence is that widget tests or any test that calls `startConversation` will permanently append to `_conversations` for the process lifetime. There is no `reset()` method. Two `InMemoryChatRepository()` instances created in the same test run share all mutations.

**Fix:** add a `@visibleForTesting static void reset()` that reassigns `_conversations` to a fresh copy of the seed data and zeros `_groupSequence`.

---

### [NIT] `officerAvatar` is module-level, not a member

**File:** `chat_repository.dart`, top of file

`officerAvatar` is a free function but it is only used inside this file. Exposing it at library scope leaks an implementation detail and pollutes the import namespace.

**Fix:** make it a private top-level function (`_officerAvatar`) or a `static` method on `InMemoryChatRepository`.

---

**TOP ISSUE:** `conversations()` returns the raw mutable `_conversations` list by reference — callers can insert, remove, and reorder without going through any repository method, silently breaking dedupe, ID generation, and ordering invariants across all views.

## Worker 02 — thread-screen

## Chat Thread Screen — QA Review

---

### [BUG] Mutating a list owned by the model outside `setState` — data integrity

**File:** `chat_thread_screen.dart`, `_markMyMessagesRead()` (~line 116)

`_markMyMessagesRead()` replaces elements in `_messages` (which is `_conversation.messages`) by index assignment. The assignment itself happens inside `setState`, but `_messages` is a direct reference to a mutable list held by the `ChatConversation` model. Any other screen holding the same `conversation` object (e.g. the conversation list) will see half-mutated state between frames if it reads the list during the timer callback window.

**Fix:** Clone the list in the model, or perform all mutations through a dedicated method on `ChatConversation` that fires its own change notification.

---

### [BUG] `_nextReply()` reads stale message count — wrong canned reply selected

**File:** `chat_thread_screen.dart`, `_scheduleAutoReply()` + `_nextReply()` (~lines 73, 112)

`_nextReplier()` is called *before* the new message is added (the auto-reply has not yet been appended), so it counts N incoming messages. `_nextReply()` is called *inside* the `Timer` callback 1.6 s later, by which time the user may have sent another message and another timer callback may be in flight. The two calls therefore may index different positions in `_cannedReplies`, producing a mismatch between the displayed "typing" name and the actual reply text.

**Fix:** Capture both values eagerly at `_scheduleAutoReply()` call time:
```dart
final replier = _nextReplier();
final reply   = _nextReply();          // capture before any new messages arrive
```
then use the captured `reply` inside the timer body.

---

### [RISK] `_replyTimer` cancel + restart doesn't guard against a second rapid send

**File:** `chat_thread_screen.dart`, `_scheduleAutoReply()` (~line 69)

If the user sends two messages within 1.6 s the first timer is cancelled correctly, but `_isContactTyping` is already `true` from the first call. The second call sets it to `true` again (no-op for UI) and schedules a new timer. This is fine for the typing indicator, but `_markMyMessagesRead()` inside the timer body will run once for the *second* reply, leaving the *first* sent message permanently in `MessageStatus.sent` state (one grey tick forever) instead of being promoted to `read`.

**Fix:** Move `_markMyMessagesRead()` outside the timer so it marks messages read at send time, or ensure the timer callback marks all pending sent messages regardless of how many were sent.

---

### [RISK] Auto-scroll fires after `dispose` if widget is popped before the timer fires

**File:** `chat_thread_screen.dart`, ~line 94

The `Timer` callback guards `mounted` before calling `setState`, but then unconditionally calls:
```dart
WidgetsBinding.instance.addPostFrameCallback((_) => _scrollToBottom());
```
after the `setState` block. If the widget is disposed between the `mounted` check and the post-frame callback execution, `_scrollToBottom()` will call `_scrollController.animateTo(...)` on a disposed controller.

**Fix:** Move the `addPostFrameCallback` inside the `if (!mounted) return;` block, or re-check `mounted` inside the callback:
```dart
WidgetsBinding.instance.addPostFrameCallback((_) {
  if (mounted) _scrollToBottom();
});
```

---

### [EDGE] Keyboard inset padding applied to a `StatelessWidget` — doesn't rebuild on keyboard show/hide

**File:** `chat_thread_screen.dart`, `_MessageInputRow.build()` (~line 284)

`MediaQuery.of(context).viewInsets.bottom` is read inside a `StatelessWidget`. Flutter will rebuild `_MessageInputRow` only when its parent calls `setState`, which happens on send/typing events but *not* purely from the keyboard appearing. On some device/OS combinations the first keyboard show won't repaint the input row until the next unrelated rebuild, causing the send bar to be obscured by the keyboard for a brief moment.

**Fix:** Make `_MessageInputRow` a `StatefulWidget` and wrap the padding logic in an `AnimatedPadding` driven by a listener, or rely on the parent `Scaffold` having `resizeToAvoidBottomInset: true` (verify it is not set to `false` anywhere in the tree) and remove the manual `viewInsets` calculation.

---

### [EDGE] Empty-list branch of `_MessageList` returns a `Center`, not a `ListView` — `scrollController` unattached

**File:** `chat_thread_screen.dart`, `_MessageList.build()` (~line 225)

When `messages.isEmpty`, the method returns a `Center(...)` widget and the `scrollController` is never attached to any `ScrollView`. The parent's `_scrollToBottom()` will call `_scrollController.hasClients` (returns `false`) and safely bail out — but `initState` calls `_scrollToBottom()` via a post-frame callback, which is silently ignored. This is benign today, but if any future path calls `_scrollController.position` before messages arrive it will throw a `StateError`.

**Fix:** No immediate code change required, but add a comment that the controller is intentionally detached when the list is empty, so a future maintainer doesn't "fix" the `hasClients` guard away.

---

### [NIT] `_StatusTicks` shows `Icons.check_rounded` for `.sent` and `Icons.done_all_rounded` for `.delivered`/`.read` — "delivered" tick identical to "read"

**File:** `chat_thread_screen.dart`, `_StatusTicks.build()` (~line 308)

`MessageStatus.delivered` falls into the `done_all_rounded` branch with grey colour (same as `sent`'s double-tick). There is no visual distinction between sent (single tick) and delivered (double tick grey) vs read (double tick blue) — which is correct — but `sent` shows a *single* tick while delivered shows a *double* tick, which is the right semantic. However `isRead` is computed from `== MessageStatus.read` while the icon branch uses `status == MessageStatus.sent` for the single tick. If `MessageStatus` ever gains more values (e.g. `failed`), those will silently render as blue double-ticks.

**Fix:** Use an exhaustive `switch` expression instead of the two-branch ternary.

---

**TOP ISSUE:** `_nextReply()` is called inside the timer closure 1.6 s after send, so rapid consecutive sends can desync the captured replier name from the actual reply text and leave earlier sent messages permanently unread — capture both `replier` and `reply` eagerly before scheduling the timer.

## Worker 03 — list-screen

## Chat List Screen — QA Review

---

### [BUG] `_loadConversations` does not reset `_loading = true` on refresh

**File:** `chat_list_screen.dart`, `_loadConversations()`

When `_loadConversations` is called after returning from a thread or creating a chat, `_loading` is never set back to `true` before the async work begins. This is only observable if the repository call takes noticeable time — the stale list stays visible rather than showing a spinner, which is benign most of the time. However, the `RefreshIndicator.onRefresh` callback calls the same method, and a slow reload will show the old list with no feedback until the future settles. More critically, if the reload throws, `_loading` is still `false` and the error renders over the old, now-invisible list — but only because the error state replaces the body. The real bug: **a background reload triggered by `_openThread` or `_startNewConversation` silently swaps data with no loading indicator and no way for the user to know a reload happened or failed.**

Fix: set `_loading = true` (and `_error = null`) in a `setState` at the top of `_loadConversations`, or add a separate `_refreshing` flag for background reloads so the old list stays visible but a banner/indicator shows activity.

---

### [BUG] Pull-to-refresh is unreachable when the list is empty or errored

**File:** `chat_list_screen.dart`, `_buildBody()`

The `RefreshIndicator` wraps only the `ListView` branch. The empty-state `Center` widget and the error-state `Center` widget are returned directly, with no scrollable ancestor. Flutter's `RefreshIndicator` requires a scrollable child to trigger the drag gesture — there is nothing to drag on those two screens. A user who hits an error or clears all conversations has no pull-to-refresh affordance.

Fix: wrap the empty/error `Center` in a `LayoutBuilder` + `SingleChildScrollView` with `physics: const AlwaysScrollableScrollPhysics()` and place a `RefreshIndicator` around it, or extract a shared `_withRefresh(Widget child)` helper used by all three branches.

---

### [BUG] `_startNewConversation` opens the thread before the list is refreshed

**File:** `chat_list_screen.dart`, `_startNewConversation()` (~line 62–76)

```dart
await _loadConversations();   // (1)
if (!mounted) return;
await _openThread(conversation); // (2) — _openThread calls _loadConversations again
```

`_openThread` unconditionally calls `_loadConversations` when it returns (line 52–55). So after a new conversation is created:
1. Reload fires (step 1).
2. Thread opens immediately.
3. Thread closes → reload fires again (from `_openThread`).

Two redundant reloads occur. More importantly, the `conversation` object passed to `_openThread` comes from either the `Navigator.push` result or `_repository.startConversation` — this object may now be stale relative to what was just reloaded into `_conversations`. If the repository assigns IDs or mutates state during `startConversation`, the thread receives the pre-reload snapshot.

Fix: remove the `await _loadConversations()` call from `_startNewConversation` and rely solely on the reload inside `_openThread`, or skip `_openThread`'s reload when navigating from a fresh creation via a parameter flag.

---

### [RISK] `_formatTime` shows only HH:mm — messages from yesterday or earlier look like today

**File:** `chat_list_screen.dart`, `_ConversationTile._formatTime()`

The timestamp always renders as `HH:mm` regardless of how old `sentAt` is. A conversation last active three days ago shows `14:32` with no date context, which is indistinguishable from one updated 10 minutes ago.

Fix: compare `sentAt.day/month/year` against `DateTime.now()` and render `"Mon"` / `"DD/MM"` for older messages, same as standard messaging apps.

---

### [EDGE] `_startNewConversation` calls `_repository.startConversation` outside of any `mounted` guard

**File:** `chat_list_screen.dart`, `_startNewConversation()` (~line 68)

```dart
conversation = await _repository.startConversation(result);
```

There is no `if (!mounted) return` after this `await`. If the widget is disposed while `startConversation` is in-flight (navigation stack pop, screen replaced), the subsequent `_loadConversations()` call will reach `setState` — which is guarded — but the intermediate `conversation` local is built from a potentially leaked `_repository` call and the method continues running pointlessly.

Fix: add `if (!mounted) return;` immediately after the `await _repository.startConversation(result)` line.

---

### [EDGE] `separatorBuilder` uses `_` twice — compile error on Dart < 3.0

**File:** `chat_list_screen.dart`, `_buildBody()` (~line 110)

```dart
separatorBuilder: (_, _) => Divider(...)
```

Dart 3.0 introduced wildcard `_` allowing duplicate discard parameters. Dart 2.x will reject this with a "duplicate parameter name" error. If the project's `sdk` lower bound in `pubspec.yaml` is `>=2.x`, this will fail for users on that SDK.

Fix: use `(_, __) =>` for Dart 2 compatibility, or confirm `pubspec.yaml` requires `sdk: '>=3.0.0'` and document it.

---

### [NIT] Error message says "Failed to load messages" but the screen loads conversations

**File:** `chat_list_screen.dart`, line ~43

```dart
_error = 'Failed to load messages: $error';
```

The list shows conversations, not messages. Inconsistent terminology will confuse officers reading the error.

Fix: `'Failed to load conversations: $error'`

---

**TOP ISSUE:** Pull-to-refresh is completely broken for the empty-state and error-state branches — a user who hits an error cannot retry without leaving and re-entering the screen.

## Worker 04 — new-chat-and-group

### `new_group_screen.dart`

**[BUG] `separatorBuilder` uses `_` twice for both parameters (line ~195)**

```dart
separatorBuilder: (_, _) => Divider(...)
```

Dart does not allow two wildcard `_` parameters in the same closure signature prior to Dart 3.7's wildcard variables feature. On SDK versions below 3.7 this is a compile error. Fix: `(_, __) =>` or `(context, index) =>`.

---

**[EDGE] `_canCreate` allows exactly 2 members but the group includes the creating officer as an implicit 3rd — or it doesn't, and a "group" of 2 is just a 1-on-1 with extra overhead (line ~135)**

```dart
bool get _canCreate =>
    _nameController.text.trim().isNotEmpty && _selectedIds.length >= 2;
```

The guard enforces ≥ 2 *selected* contacts, but it's unclear whether the current user is injected as a member inside `startGroupConversation`. If the repository already adds the caller, a 2-member selection is fine. If it doesn't, a "group" of 2 selected members with no self-inclusion is valid but worth a comment. No action needed unless the repository omits the creator — in that case enforce `_selectedIds.length >= 1` and document the invariant.

---

**[RISK] `_create` does not guard against re-entry from a double-tap before the first `setState(() => _creating = true)` frame (line ~155)**

```dart
Future<void> _create() async {
  if (!_canCreate || _creating) return;
  setState(() => _creating = true);   // <-- async gap before this applies
```

The `_creating` flag is set inside `setState`, which schedules a rebuild but the flag assignment itself is synchronous — this is actually fine. However the `TextButton.onPressed` is wired to `_canCreate && !_creating ? _create : null`, so a rapid double-tap before the first rebuild could fire `_create` twice. Fix: set `_creating = true` synchronously *before* `setState`, or use a debounce.

```dart
Future<void> _create() async {
  if (!_canCreate || _creating) return;
  _creating = true;                  // guard immediately
  setState(() {});                   // then rebuild to disable button
  ...
}
```

**[EDGE] No maximum group name length enforced (line ~219)**

`TextField` has no `maxLength`. A user can submit an arbitrarily long name that will overflow any UI that renders it. Fix: add `maxLength: 50` (or whatever the product limit is).

**[NIT] `_buildSelectionCount` hint text says "at least two members" but `_canCreate` enforces `>= 2`, so selecting exactly 2 does enable creation — the message is not misleading but it could say "at least two members" (it does). No change needed.**

Actually re-read: the message *is* correct. Skip.

---

**[EDGE] `_contacts` list is fetched independently in both `NewChatScreen` and `NewGroupScreen` (two round-trips to the same `availableContacts()` call)**

`NewChatScreen._createGroup` pushes `NewGroupScreen` which triggers a second `availableContacts()` fetch. There is no deduplication between one-to-one and group contact lists either. If `availableContacts()` is expensive (network/disk) this doubles the cost for every "New group" tap. Fix: pass the already-loaded contacts as a constructor parameter to `NewGroupScreen`, or cache at the repository layer.

### `new_chat_screen.dart`

**[EDGE] No handling for the case where the repository throws inside `_loadContacts` (line ~30)**

```dart
Future<void> _loadContacts() async {
  final contacts = await widget.repository.availableContacts();
```

An exception here leaves `_loading = true` forever — the spinner never stops and there's no error state. The same issue exists in `NewGroupScreen._loadContacts`. Fix: wrap in try/catch and set `_loading = false` + surface an error message.

**[RISK] `_createGroup` pops `NewChatScreen` with a `ChatConversation` but the caller (`new_chat_screen.dart`) is documented to pop with either a `ChatContact` *or* a `ChatConversation` — the consuming code must handle both types (line ~44)**

## Worker 05 — model-message

## Chat Message Model — QA Review

---

**[BUG] `chat_message.dart` — `copyWith` drops any new fields silently**

`copyWith` only accepts `status` as an overridable parameter. Every other field (`id`, `text`, `sentAt`, `fromMe`, `senderName`) is hard-coded to `this.*`. This means callers *cannot* patch any other field (e.g. correcting `senderName`, redacting `text`), and future fields added to the class will be invisible to `copyWith` until it's manually updated — the exact failure mode the doc-comment says it prevents.

Fix: add all fields as optional params — `copyWith({String? id, String? text, DateTime? sentAt, bool? fromMe, MessageStatus? status, String? senderName})`.

---

**[BUG] `chat_message.dart` — no `==` / `hashCode` override**

`ChatMessage` is used as a value object (immutable, `const` constructor), but without `==`/`hashCode`, two messages with identical content are never equal. This breaks list diffing, `setState` no-op detection, and any `Set<ChatMessage>` or `Map<ChatMessage, _>` usage the UI layer will almost certainly attempt.

Fix: override `==` comparing `id` only (id is the natural key), and `hashCode` as `id.hashCode`.

---

**[RISK] `chat_message.dart` — `status` defaults to `MessageStatus.sent` for inbound messages**

The doc-comment says inbound messages "always read as delivered", but the constructor default is `sent`. Any code that constructs an inbound message (`fromMe: false`) without explicitly passing `status: MessageStatus.delivered` will show a single outbound-style tick on a received message. The model doesn't enforce the invariant; it only documents it.

Fix: assert the invariant in the constructor body — `assert(fromMe || status == MessageStatus.delivered, 'Inbound messages must have status delivered')` — and/or set the default conditionally via a factory constructor.

---

**[RISK] `chat_message.dart` — `sentAt` is not stored as UTC**

`DateTime.now()` at the call site returns local time; `DateTime.now().toUtc()` is not enforced by the model. When messages from two officers in different time zones are sorted by `sentAt`, ordering will be wrong. Even in a single-device in-memory app this is a latent bug the moment time zones become relevant (device locale change, DST crossing).

Fix: add `assert(sentAt.isUtc)` or normalise in the constructor: `sentAt = sentAt.toUtc()`.

---

**[EDGE] `chat_message.dart` — `text` can be an empty string**

No validation guards against `text.isEmpty`. An empty bubble (e.g. from a UI race or accidental send) will render as a zero-height widget with only tick marks, which is visually broken.

Fix: add `assert(text.isNotEmpty, 'Message text must not be empty')`.

---

**[NIT] `chat_message.dart` — missing `attachmentUrl` / `messageType` field**

The UI almost always needs to distinguish text-only from image/file messages. Introducing `messageType` later will require a breaking change to every constructor call site. Not a bug today, but a near-certain omission.

Fix: add `final MessageType type` (enum: `text`, `image`, `file`) now, defaulting to `text`, so call sites are unaffected.

---

**TOP ISSUE:** `copyWith` silently ignores every field except `status`, making the model effectively immutable in all the wrong ways — read-receipt updates will work, but any other in-place mutation (text redaction, sender correction, future fields) is a silent no-op.

## Worker 06 — model-conversation

## Chat Conversation Model — QA Findings

---

### [BUG] `lastMessage` relies on insertion order, not `sentAt`

**File:** `chat_conversation.dart`, `lastMessage` getter (~line 44)

`messages.last` returns the most-recently *appended* element, not the chronologically latest message. If messages ever arrive out of order (network reorder, initial load from a map/set, etc.) the conversation list will show the wrong preview and sort key.

**Fix:** `return messages.reduce((a, b) => a.sentAt.isAfter(b.sentAt) ? a : b);` (or keep the list sorted on insert).

---

### [BUG] `_seenInbound` cannot be provided at construction — all messages appear unread on rebuild

**File:** `chat_conversation.dart`, `_seenInbound` field (~line 18)

`_seenInbound` is always initialised to `0`. In Flutter, `ChatConversation` objects are regularly recreated (provider refresh, hot-reload, routing). Every reconstruction makes `unreadCount` equal to the total inbound message count, even for threads the user has already read. There is no constructor parameter or factory to restore the read cursor.

**Fix:** Add `int seenInbound = 0` as a named constructor parameter and initialise `_seenInbound` from it; expose a `copyWithSeenInbound` helper so callers can persist and restore the cursor.

---

### [RISK] `messages` is a mutable list exposed on a logically-immutable object

**File:** `chat_conversation.dart`, field declaration (~line 13)

`final List<ChatMessage> messages` prevents reassigning the reference but not mutations (`messages.add(...)`, `messages.removeAt(...)`). External code can add/remove messages without `_seenInbound` ever updating, silently corrupting `unreadCount`.

**Fix:** Store as `List<ChatMessage> _messages` (private), expose `List<ChatMessage> get messages => List.unmodifiable(_messages);`, and add an `addMessage(ChatMessage m)` method that owns mutation.

---

### [EDGE] Negative `_seenInbound` clamp hides inconsistent state after message deletion

**File:** `chat_conversation.dart`, `unreadCount` getter (~line 60)

```dart
final unread = _inboundCount - _seenInbound;
return unread < 0 ? 0 : unread;
```

If an inbound message is deleted (possible once the mutable list is accessible), `_inboundCount` drops below the already-snapshotted `_seenInbound`. The clamp silently hides the corruption. Any subsequent new inbound message adds `1` to `_inboundCount` but the badge stays at `0` until `_inboundCount` catches back up to `_seenInbound`.

**Fix:** Assert or reset `_seenInbound = min(_seenInbound, _inboundCount)` at the top of `unreadCount` rather than only clamping the result.

---

### [EDGE] Sentinel `ChatMessage` leaks into comparison/sort logic

**File:** `chat_conversation.dart`, `lastMessage` getter (~line 46)

The empty sentinel uses `sentAt: DateTime(2000)`. Any code that sorts conversations by `lastMessage.sentAt` will push empty threads to the very bottom but before any message genuinely sent in January 2000. A more obvious sentinel (e.g. `DateTime.fromMillisecondsSinceEpoch(0)`) or a nullable `ChatMessage? get lastMessage` makes the empty-thread case unambiguous.

**Fix:** Return `null` and update callers — eliminates the hidden date magic and forces display code to handle the empty state explicitly.

### [NIT] `_inboundCount` is recomputed on every `unreadCount` read and `markRead` call

## Worker 10 — edge-cases

## Chat Feature QA — Edge Case Review

---

### [BUG] Duplicate message IDs on same-millisecond sends
**`chat_thread_screen.dart` — `_sendMessage()` ~line 51, `_scheduleAutoReply()` timer callback ~line 79**

Both outgoing and auto-reply messages use `DateTime.now().millisecondsSinceEpoch` as their ID suffix:
```dart
id: 'msg-sent-${DateTime.now().millisecondsSinceEpoch}',
// …and inside the timer:
id: 'msg-reply-${DateTime.now().millisecondsSinceEpoch}',
```
On a fast device (or a test loop), two sends within the same millisecond produce identical IDs. The auto-reply fires ~1600 ms later, so the `msg-sent-` and `msg-reply-` namespaces don't collide with each other — but two back-to-back user sends absolutely can. Once IDs are used as `ValueKey` or for dedup, this breaks silently.

**Fix:** Replace with a static monotonic counter — `static int _seq = 0; id: 'msg-${++_seq}'`.

---

### [BUG] Long unbreakable text overflows/clips in the bubble
**`chat_thread_screen.dart` — `_BubbleBody.build()`, `Text(message.text, …)` ~line 217**

The `Text` widget defaults to `softWrap: true` but can only break at word boundaries. A single long token — a URL, a case-file reference like `EX-2026-0891/DETACHMENT-ALPHA-TEAM-WHISKEY`, or a base64 string — will exceed the `maxWidth * 0.72` constraint and be clipped with no indication to the reader. There is no `overflow` or `maxLines` set.

**Fix:** Add `overflow: TextOverflow.ellipsis` (or `visible`) to the message `Text` widget, or wrap it in a `SelectionArea` with `softWrap: true, overflow: TextOverflow.visible` so the box expands rather than clips.

---

### [BUG] `_nextReplier()` and `_nextReply()` indexes can desync on rapid sends
**`chat_thread_screen.dart` — `_scheduleAutoReply()` ~lines 66, 87**

`_nextReplier()` counts non-`fromMe` messages at schedule time and captures the result in `replier`. `_nextReply()` re-counts non-`fromMe` messages at fire time (1600 ms later, inside the `Timer` callback). If the user sends multiple messages rapidly:

1. User sends msg A → `_scheduleAutoReply()`, `replier = members[N % 3]`, timer T1 starts.
2. User sends msg B → T1 cancelled, `_scheduleAutoReply()`, `replier = members[N % 3]` (same N, still no reply yet), T2 starts.

In this specific scenario the counts align. **But** `_nextReply()` is computed fresh inside the callback, while `replier` was captured at schedule time. If any other code path mutates `_messages` between those two moments (e.g., a future "receive" push), the canned reply index and the displayed sender name will diverge, producing an attribution mismatch ("Copy that." credited to the wrong officer). Capture `_nextReply()` at the same point as `_nextReplier()` to keep them in sync.

**Fix:** Capture `final reply = _nextReply();` immediately after `final replier = _nextReplier();` in `_scheduleAutoReply()` and use the captured value inside the timer lambda.

---

### [RISK] Empty or whitespace-only group name accepted silently
**`chat_repository.dart` — `startGroupConversation()` ~line 49**

`members.isEmpty` is validated, but `name` is never validated. Calling `startGroupConversation('   ', members)` creates a group with a blank display name — the `ChatGroup.name` becomes `'   '`, `avatarInitials` (presumably derived from `name`) would be a space or crash depending on implementation, and the list entry renders as empty.

**Fix:** Add `if (name.trim().isEmpty) throw ArgumentError('Group name cannot be blank.');` before the `_groupSequence++`.

---

### [RISK] `addPostFrameCallback` scroll after widget disposal
**`chat_thread_screen.dart` — `_sendMessage()` ~line 57, timer callback ~line 85**

```dart

```
This callback is registered unconditionally before `_scheduleAutoReply()`. If the user sends a message and immediately navigates away (pop), the callback fires in the next frame after `dispose()` has been called. The `_scrollController.hasClients` guard should save you in release mode, but in debug builds `ScrollController.hasClients` may trigger `assert(!_debugDisposed)` depending on Flutter version.

**Fix:** Capture a mounted check in the callback: `addPostFrameCallback((_) { if (mounted) _scrollToBottom(); });`.

**`chat_repository.dart` — `startGroupConversation()` ~line 49**

Only `members.isEmpty` is rejected. A one-member group is semantically a direct message and will appear in the group list with a single participant — no crash, but confusing state and `_nextReplier()` will always return `members[0].name`.

### `lib/services/chat/chat_repository.dart`

**[BUG] `conversations()` returns `_conversations` in insertion order — no recency sort**

`_conversations.insert(0, …)` puts new threads at the top, but existing threads never move. After opening `conv-006`, sending three messages, and navigating back, `conv-006` stays at index 6. `_loadConversations()` in `ChatListScreen` returns the same static list with no sorting step.

**[BUG] `NewGroupScreen._loadContacts()` calls `availableContacts()`, which silently excludes contacts already in a 1-to-1 thread from group member selection**

`availableContacts()` is explicitly documented as "officers not already in a one-to-one thread." Once a 1:1 with, say, Marlon Stewart is started, `availableContacts()` drops him from the result set — so `NewGroupScreen._contacts` never includes him and he can never be added to a group.

*Fix:* Add a separate `Future<List<ChatContact>> allContacts()` method (or expose `_roster`) and use it in `NewGroupScreen._loadContacts()`.

### `lib/screens/chat/chat_thread_screen.dart`

**[RISK] `_nextReply()` and `_nextReplier()` compute rotation index from `_messages` at different points in time**

`_nextReplier()` is evaluated eagerly in `_scheduleAutoReply()` (before the timer fires), while `_nextReply()` is evaluated 1 600 ms later inside the timer callback. On rapid consecutive sends the timer is cancelled and re-scheduled, so `_nextReplier()` captures the count at send-time, but `_nextReply()` re-counts at fire-time after `_markMyMessagesRead()` has been called. If send-burst yields different counts, the displayed typing name and the `senderName` written into the message bubble can diverge.

*Fix:* Capture `_nextReply()` alongside `_nextReplier()` at the same call-site, before the timer, and pass both into the closure.

**[EDGE] `_nextReplier()` group rotation counts ALL historical inbound messages, not just replies since the thread was opened**

The seeded `conv-grp-901` already has 2 inbound messages. On the first auto-reply, `replyCount = 2`, so `members[2 % 3]` = members[2] (Keisha Morgan) — the typing indicator shows a random mid-list officer instead of the expected first member.

*Fix:* Track a `_autoReplyIndex` counter on the state instead of counting all inbound messages.
