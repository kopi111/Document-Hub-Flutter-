## Worker 01 — repository-logic

## Chat Repository — QA Findings

---

### [BUG] `_conversations` is `static final` on a mutable list — state shared across all instances

**Location:** `chat_repository.dart`, `_conversations` declaration

`_conversations` is `static final List<ChatConversation>`. Every call to `_conversations.insert(0, ...)` in `startConversation` and `startGroupConversation` writes to a single process-wide list. Creating a fresh `InMemoryChatRepository()` (e.g. after DI reinit, hot restart, or in tests) does **not** reset this list — all previously inserted conversations persist. Tests written against this class will leak state into each other.

**Fix:** Make `_conversations` an instance field initialized from a static seed via `List.of(_seed)`.

---

### [BUG] `_groupSequence` is an instance field but `_conversations` is static — duplicate IDs possible

**Location:** `chat_repository.dart`, line `int _groupSequence = 0;`

Because `_conversations` is shared (static) but `_groupSequence` is per-instance, two independent repository instances will both start their counters at `0` and generate IDs `grp-new-1`, `grp-new-2`, … — colliding in the same list. Even with a single instance, if the repository is recreated the counter resets while the old groups remain.

**Fix:** Declare `static int _groupSequence = 0;` to align lifetime with `_conversations`; or, better, fix the static sharing bug above and keep both as instance state.

---

### [BUG] `startGroupConversation` dereferences `members.first` without a guard

**Location:** `chat_repository.dart`, inside `startGroupConversation`

```dart
final conversation = ChatConversation(
  id: 'conv-${group.id}',
  contact: members.first,   // throws StateError if members is empty
  ...
);
```

No validation that `members` is non-empty. Callers (e.g. a UI that ships an empty selection) will get an unhandled `Bad state: No element`.

**Fix:** Add `assert(members.isNotEmpty)` or throw an `ArgumentError` before the group is constructed.

---

### [RISK] `conversations()` exposes the internal mutable list directly

**Location:** `chat_repository.dart`, `conversations()` method

```dart
Future<List<ChatConversation>> conversations() async => _conversations;
```

Any caller that receives this list can mutate it (`.add`, `.remove`, `.clear`) without going through the repository. Combined with the static lifetime, a single rogue call can corrupt the seed state for the entire session.

**Fix:** Return `List.unmodifiable(_conversations)` or a shallow copy via `List.of(_conversations)`.

---

### [RISK] `_groupMembers` aliases entries from `_roster` by reference

**Location:** `chat_repository.dart`, `_groupMembers` declaration

```dart
static final List<ChatContact> _groupMembers = [
  _roster[0], _roster[2], _roster[5],
];
```

`_groupMembers` holds the same object references as `_roster`. If `ChatContact` exposes any mutable fields (e.g. `isOnline` updated at runtime), mutating a contact through `_roster` silently changes the same object visible in the seeded group's member list — and vice versa. This is invisible aliasing.

**Fix:** Copy at construction time: `ChatContact.copyWith(...)` or `ChatContact(id: _roster[0].id, ...)`.

---

### [EDGE] `startGroupConversation` has no dedupe check and no name validation

**Location:** `chat_repository.dart`, `startGroupConversation`

Unlike `startConversation`, there is no guard against creating duplicate groups (same name, same members). Tapping "Create" twice rapidly inserts two identical groups. An empty `name` string is also accepted silently.

**Fix:** Either check for an existing group with the same name, or (at minimum) assert `name.isNotEmpty`.

---

### [NIT] `availableContacts` silently omits group-thread members from no 1:1 thread

**Location:** `chat_repository.dart`, `availableContacts()`

The filter only excludes a contact if they appear in a **non-group** conversation's `contact.id`. Contacts who are *only* group members (off-201, off-203, off-206 in the seed) are correctly kept available for 1:1 threads — but the comment on the abstract method ("those not already in a one-to-one thread") is the only documentation of this decision. Any future maintainer who adds "exclude group members too" would silently change the behavior.

**Fix:** Add an inline comment clarifying that group membership intentionally does not disqualify a contact.

---

**TOP ISSUE:** `_conversations` is a `static final` mutable list — all repository instances share and permanently accumulate state, breaking hot-restart behaviour and making the class untestable in isolation.

## Worker 02 — thread-screen

## Chat Thread Screen — QA Review

---

### [BUG] `_sendMessage` — `setState` wraps `_inputController.clear()` unnecessarily but, more critically, `_messages` is mutated outside of the owning object's `setState`

**File:** `chat_thread_screen.dart`, `_sendMessage` / `_markMyMessagesRead` / `_scheduleAutoReply`

`_messages` is a getter that returns `_conversation.messages` — a `List` that lives inside `ChatConversation`, which is passed in via `widget.conversation`. Every `.add()` and index-assignment on `_messages` mutates that external list directly. The `setState` call notifies Flutter that *this* widget rebuilt, but the data owner is outside the widget tree — so if `ChatConversation` is shared or re-used elsewhere (e.g. the conversation list screen holding unread counts), those callers see silent mutation with no rebuild triggered.

**Fix:** Either copy the list into local state in `initState` (`_localMessages = List.of(widget.conversation.messages)`) and operate on that, or lift state to a proper store/notifier.

---

### [BUG] `_scrollToBottom` called before the new item has been laid out in `_sendMessage`

**File:** `chat_thread_screen.dart` ~line 62

```dart
setState(() {
  _messages.add(outgoing);
  _inputController.clear();
});
WidgetsBinding.instance.addPostFrameCallback((_) => _scrollToBottom());
```

`addPostFrameCallback` fires after the *current* frame commits. However `setState` schedules a rebuild for the *next* frame — so the post-frame callback registered here fires after the frame that triggered `setState`, which may be the same frame before the list has re-laid-out with the new item. `maxScrollExtent` will be the value from before the new item was added, and the scroll will land one item short.

**Fix:** Move the `addPostFrameCallback` call *inside* the callback that runs after the rebuild by calling it from within a second `addPostFrameCallback`, or use `SchedulerBinding.instance.addPostFrameCallback` after the setState completes by nesting: fire it inside the Timer callback pattern used in `_scheduleAutoReply` (which correctly schedules scroll after its own `setState`).

---

### [BUG] `_nextReply` / `_nextReplier` both read `_messages` length *before* the new reply is appended

**File:** `chat_thread_screen.dart`, `_scheduleAutoReply` timer callback ~line 76

```dart
setState(() {
  _isContactTyping = false;
  _markMyMessagesRead();   // <-- mutates _messages
  _messages.add(           // <-- appended after _nextReply() was called
    ChatMessage(..., text: _nextReply(), ...),
  );
});
```

`_nextReply()` is evaluated during the `setState` call, *after* `_markMyMessagesRead()` runs — which does **not** change the count of `!fromMe` messages, so `_nextReply` is fine here. But `_nextReplier()` is called *before* `setState` at line ~70, also before the add — so that count is consistent. These are actually correct as written, but:

`_nextReplier` and `_nextReply` compute the same `replyCount` independently, creating a latent coupling bug: if either method is ever reordered or called an extra time, they'll diverge.

**Fix:** Compute `replyCount` once and pass it to both helpers, or merge them into a single `_nextReplyPayload()` returning a record/tuple.

---

### [RISK] `_replyTimer` callback accesses `_messages` (external mutable list) after a 1.6 s delay with no guard on widget replacement

**File:** `chat_thread_screen.dart` ~line 73

The `mounted` check is present and correct. However if the parent rebuilds and passes a *different* `ChatConversation` object (unlikely but valid Flutter widget contract), `_conversation` still points to the old one via `widget.conversation` — but `widget` is now the new widget. The `mounted` guard does not protect against this.

**Fix:** Cache `widget.conversation` in a local `late` field during `initState` so the timer closure closes over a stable reference.

---

### [EDGE] `onSubmitted` fires on physical Enter on desktop/web but does not unfocus / re-focus the field, causing the keyboard to dismiss on mobile

**File:** `chat_thread_screen.dart`, `_MessageInputRow` ~line 390

```dart
onSubmitted: (_) => onSend(),
```

On mobile, `onSubmitted` is called when the user taps the IME "send" action. After `onSend()` clears the controller, the `TextField` loses its editing state and the soft keyboard may dismiss. The user must re-tap the field to continue typing. This is a regression compared to WhatsApp-style UIs where the field retains focus.

**Fix:** After clearing the controller in `_sendMessage`, call `FocusScope.of(context).requestFocus(_inputFocusNode)` using a stored `FocusNode`.

---

### [EDGE] `_MessageList` switches between an empty-state `Center` widget and a `ListView` — the `scrollController` is never attached when the list is empty, so the first `_scrollToBottom` after the very first message finds `!_scrollController.hasClients`

**File:** `chat_thread_screen.dart`, `_MessageList.build` ~line 240 and `_scrollToBottom` ~line 120

When the conversation starts with zero messages, `_scrollController` has no clients. `_scrollToBottom` guards with `if (!_scrollController.hasClients) return` — so the scroll is silently skipped after sending the first message. The first sent message appears, but the view does not scroll (though with one item this is usually harmless, it breaks if content already exceeds screen height).

**Fix:** Always render the `ListView` (with `itemCount: 0` when empty) so the scroll controller is always attached; show the empty-state as a `SliverFillRemaining` or as the `itemBuilder`'s sole item.

---

### [EDGE] `_BubbleFooter` row always aligns `mainAxisAlignment: MainAxisAlignment.end` but `mainAxisSize: MainAxisSize.min` — on very short messages the time+tick may overflow or clip the bubble width

**File:** `chat_thread_screen.dart`, `_BubbleFooter` ~line 330

The bubble constrains itself to `maxWidth: 0.72 * screenWidth`. The footer is `Row(mainAxisSize: MainAxisSize.min)` so it can be wider than the message text on very short messages (e.g. "K"), pushing the bubble wider than the text alone. This is usually fine, but on narrow screens with long timestamps it may overflow the 72% cap.

**Fix:** Wrap footer in `Align(alignment: Alignment.centerRight)` and use a `Wrap` or ensure the bubble `Column` is `crossAxisAlignment.stretch` so the footer always fits.

---

### [NIT] `_StatusTicks` ignores `MessageStatus.delivered` — it maps both `delivered` and `read` to `done_all_rounded`

**File:** `chat_thread_screen.dart`, `_StatusTicks` ~line 360

```dart
final icon = status == MessageStatus.sent ? Icons.check_rounded : Icons.done_all_rounded;
```

If `MessageStatus` has a `delivered` value, it renders identical to `read` (double tick, but grey instead of blue). This is probably intentional for the in-memory demo but is a silent semantic gap.

**Fix:** Add an explicit `switch` over all enum values or add a comment noting `delivered` renders as grey double-tick by design.

---

## TOP ISSUE:

**[BUG] `_messages` directly mutates the `ChatConversation` passed in from the parent** — shared mutable state with no ownership boundary means silent cross-screen data corruption and missed rebuilds as the conversation list grows.

## Worker 03 — list-screen

## Chat List Screen — QA Review

### Findings

---

**[BUG] `_openThread` triggers a repaint but never reloads data**
`chat_list_screen.dart` · `_openThread` (line ~55)

```dart
if (!mounted) return;
setState(() {});   // ← empty setState, _conversations is stale
```

After returning from `ChatThreadScreen`, the list re-renders from cached `_conversations`. Unread counts and last-message previews show the pre-visit snapshot. Fix: replace `setState(() {})` with `_loadConversations()`.

---

**[BUG] `_error` is never cleared on a successful reload**
`chat_list_screen.dart` · `_loadConversations` success branch (line ~40)

```dart
setState(() {
  _conversations = result;
  _loading = false;
  // _error is never reset to null
});
```

If the first load fails (`_error` is set) and the user somehow triggers a pull-to-refresh that succeeds, `_buildBody` still returns the error view because `_error != null` is checked before `_conversations.isEmpty`. The list is never displayed. Fix: add `_error = null` inside the success `setState`.

---

**[RISK] Error and empty states are not scrollable — pull-to-refresh is unreachable**
`chat_list_screen.dart` · `_buildBody` (lines ~100–115)

`RefreshIndicator` only wraps the `ListView`, which is only built when `_conversations.isNotEmpty`. A user stuck in the error or empty state has no way to retry — there is no retry button and no gesture surface. Fix: wrap error/empty `Center` widgets in a `LayoutBuilder` + `SingleChildScrollView` (with `physics: AlwaysScrollableScrollPhysics`) inside the `RefreshIndicator`, or add an explicit retry button.

---

**[RISK] `_startNewConversation` opens the thread even when `_loadConversations` failed silently**
`chat_list_screen.dart` · `_startNewConversation` (lines ~65–80)

`_loadConversations` swallows its exception and sets `_error`. The caller doesn't inspect the outcome, so after a failed reload the code continues to `_openThread(conversation)`. The thread opens successfully but the conversation list is now in error state. Fix: have `_loadConversations` rethrow (or return a `bool`), and guard the `_openThread` call on success only.

---

**[EDGE] `conversation.lastMessage` assumed non-null for newly-created conversations**
`chat_list_screen.dart` · `_ConversationTile.build` (line ~145)

```dart
final last = conversation.lastMessage;
final hasMessages = last.text.isNotEmpty;
```

`_startNewConversation` can create a conversation with zero messages. If the model's `lastMessage` field is nullable (common when a thread has never been sent to), `last.text` throws a null-dereference before the `hasMessages` guard can protect anything. Fix: null-check `last` before accessing `.text`.

---

**[EDGE] `_formatTime` shows only HH:MM regardless of message age**
`chat_list_screen.dart` · `_ConversationTile._formatTime` (line ~220)

A conversation from three days ago shows `14:32`, indistinguishable from one sent an hour ago. This is standard for most messengers but is a footgun for an officer comms tool where recency matters. Fix: show day name or date when `sentAt` is not today.

---

**[NIT] `separatorBuilder: (_, _)` requires Dart ≥ 3.0 wildcard support**
`chat_list_screen.dart` · `_buildBody` ListView (line ~120)

Using `_` twice as distinct positional parameter names is only legal under Dart 3's wildcard pattern. If the project targets Dart 2.x or an older Flutter stable, this is a compile error. Fix: use named parameters `(context, index)` or verify the minimum SDK.

---

**TOP ISSUE:** `_openThread` calls `setState(() {})` instead of `_loadConversations()` — every return from a thread leaves stale unread counts and last-message previews, making the list permanently out of sync with reality.

## Worker 04 — new-chat-and-group

## Chat / Group Creation — QA Findings

---

### `new_group_screen.dart`

**[BUG] `separatorBuilder` uses `_` twice for both parameters (~line 258)**

```dart
separatorBuilder: (_, _) => Divider(...)
```

Dart does not allow two unnamed discard parameters with the same identifier `_` in the same parameter list (this is valid in Dart 3.0+ only if the language version opt-in is present, and even then it is fragile tooling-wise). On Dart < 3.0 this is a compile error. Fix: use `(_, __)` or `(context, index)`.

---

**[BUG] `_creating` is set to `true` but never reset to `false` on error (~line 208)**

```dart
Future<void> _create() async {
    if (!_canCreate || _creating) return;
    setState(() => _creating = true);
    ...
    final conversation = await widget.repository
        .startGroupConversation(...);
    if (!mounted) return;   // ← if an exception is thrown above, _creating stays true
    Navigator.of(context).pop<ChatConversation>(conversation);
}
```

If `startGroupConversation` throws, `_creating` is permanently `true` and the Create button remains disabled forever (within that screen instance). Fix: wrap the `await` in a `try/finally` and reset `_creating` in the `finally` block.

---

**[EDGE] `_canCreate` requires `>= 2` selected members but the helper text says "at least two members" — the current user (self) is excluded from the roster by `availableContacts()` but that assumption is unverified here (~line 195)**

If `availableContacts()` ever includes the current user, a group of "current user + 1 other" would pass the `_selectedIds.length >= 2` guard but actually be a two-person group without the real intent. The guard should be documented or the repository contract made explicit. Not a code defect per se, but a latent [RISK] if the data layer changes.

---

**[EDGE] `members` list is built by filtering `_contacts` against `_selectedIds`, but `_contacts` is loaded once and never refreshed (~line 210)**

```dart
final members = _contacts
    .where((contact) => _selectedIds.contains(contact.id))
    .toList(growable: false);
```

If a contact is removed/deactivated between the time the list loads and the time the user presses Create, the selected ID remains in `_selectedIds` but is absent from `_contacts`, so it is silently dropped. The resulting group could have fewer members than the user intended — potentially below the two-member minimum — without any feedback. Fix: validate `members.length >= 2` just before calling `startGroupConversation` and surface an error if not.

---

**[EDGE] No max-length enforcement on the group name field (~line 230)**

`TextField` has no `maxLength` or `inputFormatters` constraint. A user can enter an arbitrarily long name. Fix: add `maxLength: 64` (or whatever the domain ceiling is).

---

**[NIT] `_nameController.addListener(() => setState(() {}))` rebuilds the entire widget on every keystroke (~line 176)**

`setState` with an empty closure is the idiomatic pattern here, but it causes a full `_NewGroupScreenState` rebuild for each character typed. `ValueListenableBuilder` wrapping only the affected widgets (the name field border and the Create button) would be more efficient. Low priority for an in-memory feature, but worth noting.

---

### `new_chat_screen.dart`

**[RISK] `_createGroup` pops `NewGroupScreen` and immediately pops `NewChatScreen` with the result, but there is no guard against the case where `NewChatScreen` is no longer the top route (~line 47)**

```dart
if (!mounted || conversation == null) return;
Navigator.of(context).pop(conversation);
```

`mounted` checks widget attachment, not whether the route is still on top of the navigator. If the user navigates away (back button) while `NewGroupScreen` is animating/resolving, `Navigator.of(context).pop(conversation)` could pop an unexpected route. Fix: use `Navigator.of(context).canPop()` before popping, or use a named route/result callback pattern.

---

**[NIT] `availableContacts()` is called independently in both `NewChatScreen` and `NewGroupScreen`, resulting in two separate async fetches of the same data (~lines 31, 176 respectively)**

If the user taps "New group," `NewGroupScreen` re-fetches the full contact list. For an in-memory repo this is trivial, but the contacts could instead be passed from parent to child. Low priority.

---

## TOP ISSUE:

**`_creating` is never reset on exception in `_create()`, permanently disabling the Create button if `startGroupConversation` throws.**

## Worker 05 — model-message

## Chat Message Model — QA Review

---

### Findings

---

**[BUG] `chat_message.dart` — Wrong default for `status`**

```dart
this.status = MessageStatus.read,   // line ~22
```

A freshly constructed outbound message defaults to `read` (double blue ticks). Every new message will display as already-read the instant it is created, before it has even been handed to any delivery layer. The default must be `MessageStatus.sent`.

**Fix:** `this.status = MessageStatus.sent`

---

**[RISK] `chat_message.dart` — No `==` / `hashCode`**

Without overriding equality, any list diffing, `contains()` check, or state-management dirty detection (e.g. Riverpod `select`, `ListenableBuilder`) falls back to reference identity. When a message is replaced with an updated copy (status change `sent → delivered → read`), widgets that depend on equality will not rebuild — or will spuriously rebuild — depending on whether a new object was allocated.

**Fix:** Add `@override bool operator ==` comparing `id`, and a matching `hashCode`.

---

**[RISK] `chat_message.dart` — No `copyWith`**

All fields are `final`, which is correct for immutability. But status transitions (`sent → delivered → read`) require replacing the object. Without `copyWith`, every call site must reconstruct the full message manually, making it trivial to accidentally drop fields (e.g. `senderName`).

**Fix:** Add a `copyWith({MessageStatus? status, ...})` method.

---

**[EDGE] `chat_message.dart` — Inbound message `status` is semantically undefined but defaults to `read`**

The doc comment says inbound messages "ignore" `status`, yet the field is typed `MessageStatus` (non-nullable) and defaults to `read`. Any UI code that checks `message.status == MessageStatus.read` without guarding on `fromMe` will incorrectly treat inbound messages as read-confirmed. Making the field `MessageStatus?` (null = inbound / not applicable) eliminates the ambiguity at the type level.

**Fix:** `final MessageStatus? status;` with a `null` default, and guard all tick-rendering code on `fromMe == true`.

---

**[EDGE] `chat_message.dart` — `sentAt` has no UTC enforcement**

`DateTime` in Dart can be local or UTC; `DateTime.now()` returns local. If any call site mixes local and UTC `DateTime` instances, chronological sorting of messages will silently produce wrong order when the device timezone offset is non-zero or changes (e.g. DST, travel).

**Fix:** Document that callers must pass `DateTime.now().toUtc()`, or enforce it in the constructor body: `sentAt = sentAt.toUtc()`.

---

**[NIT] `chat_message.dart` — No `toString`**

Without a `toString` override, log output and Flutter DevTools show only the default object hash, making it difficult to inspect message state during debugging.

**Fix:** Add `@override String toString() => 'ChatMessage($id, fromMe:$fromMe, status:$status)'`.

---

**TOP ISSUE:** The `status` default of `MessageStatus.read` causes every new outbound message to render as already-read the moment it is created — fix that default to `MessageStatus.sent` before anything else ships.

## Worker 06 — model-conversation

## Code Review: `lib/models/chat/chat_conversation.dart`

---

### Findings

---

**[BUG] `unreadCount` has no read-state tracking — counts will never decrease**

`chat_conversation.dart`, `unreadCount` getter

```dart
int get unreadCount => messages.where((m) => !m.fromMe).length;
```

This counts *every* received message, forever. A conversation with 200 read messages permanently shows `unreadCount = 200`. Neither `ChatMessage` nor `ChatConversation` carries a `isRead`, `readAt`, or `lastReadMessageId` field, so there is no way for this count to ever reach zero after messages arrive.

**Fix:** Add `String? lastReadMessageId` to `ChatConversation` and count only messages after that cursor, e.g.:
```dart
int get unreadCount {
  if (lastReadMessageId == null) return messages.where((m) => !m.fromMe).length;
  final idx = messages.indexWhere((m) => m.id == lastReadMessageId);
  return idx == -1 ? 0 : messages.skip(idx + 1).where((m) => !m.fromMe).length;
}
```

---

**[BUG] Sentinel `id: ''` collides across all empty conversations**

`chat_conversation.dart`, `lastMessage` getter (~line 37)

```dart
return ChatMessage(id: '', text: '', sentAt: DateTime(2000), fromMe: false);
```

Every empty conversation returns a sentinel with an empty-string `id`. If any caller uses `lastMessage.id` as a `ValueKey`, map key, or deduplication key, all empty threads silently alias each other.

**Fix:** Use the parent conversation's own ID: `id: '${id}_sentinel'`

---

**[BUG] Sentinel `sentAt: DateTime(2000)` corrupts sort order and date display**

`chat_conversation.dart`, `lastMessage` getter (~line 38)

Any list that sorts conversations by `lastMessage.sentAt` descending places empty threads at the very bottom as if they were from the year 2000 — correct by accident. Ascending sort puts them at the very top — wrong. Any UI that *displays* the date (e.g., a `timeago` label) will render "Jan 2000" instead of blank.

**Fix:** Make `lastMessage` nullable — `ChatMessage? get lastMessage => messages.isEmpty ? null : messages.last` — and guard at the display layer. This is the correct contract; the "avoids null" justification pushes the problem downstream rather than solving it.

---

**[RISK] `messages` list is externally mutable, breaking derived state**

`chat_conversation.dart`, field declaration (~line 12)

```dart
final List<ChatMessage> messages;
```

`final` pins the *reference*, not the contents. Any caller can do `conversation.messages.add(m)` or `conversation.messages.clear()`, silently invalidating `lastMessage` and `unreadCount` with no notification path.

**Fix:**
```dart
final List<ChatMessage> _messages;
List<ChatMessage> get messages => List.unmodifiable(_messages);
```

---

**[RISK] No invariant enforcing that a group `contact` is actually a member of the group**

`chat_conversation.dart`, constructor

The doc-comment says the `contact` field for a group "holds a representative member", but the constructor accepts any `ChatContact` with no validation. A caller can legally pass an officer who is not in the group, producing a corrupt representative (wrong initials, wrong avatar, wrong rank in the subtitle).

**Fix:** Add a debug assertion:
```dart
assert(!isGroup || group!.members.any((m) => m.id == contact.id),
    'Group representative must be a member of the group');
```
(Assumes `ChatGroup.members` is iterable; adjust to the actual API.)

---

**[EDGE] `isOnline` presence dot shown for groups via `anyOnline`**

`chat_conversation.dart`, `isOnline` getter

```dart
bool get isOnline => group?.anyOnline ?? contact.isOnline;
```

Showing a presence dot when *any* member of a group is online is non-standard UX and will confuse users (the dot implies the conversation partner is available, not "at least one of 15 officers is logged in"). Most group chat UIs suppress the presence indicator entirely.

**Fix:** `bool get isOnline => isGroup ? false : contact.isOnline;`

---

**[NIT] Blank sentinel `text: ''` for empty thread is an empty string, not a placeholder**

`chat_conversation.dart`, `lastMessage` getter

Display code that does `lastMessage.text` will render an empty string rather than "No messages yet" or similar. If the sentinel pattern is kept, this is a silent UX gap.

**Fix:** Use a recognizable sentinel text (`text: ''` is fine only if every caller guards on `messages.isEmpty` first — which defeats the purpose of the sentinel).

---

## Worker 10 — edge-cases

## Chat Feature QA — Edge Case Analysis

---

### [BUG] `chat_repository.dart` — `startGroupConversation`, `members.first` with empty list

**Location:** `InMemoryChatRepository.startGroupConversation`, line building `ChatConversation(contact: members.first, …)`.

If the caller passes an empty `members` list, `members.first` throws `StateError: No element`. There is no guard.

**Fix:** `if (members.isEmpty) throw ArgumentError('Group must have at least one member');` before accessing `members.first`.

---

### [BUG] `chat_thread_screen.dart` — `_nextReplier` divides by zero when group has zero members

**Location:** `_nextReplier()` → `replyCount % members.length`.

A `ChatGroup` with an empty members list reaches `% 0`, which throws `IntegerDivisionByZeroException`. The repository bug above currently prevents this state from being created, but defensive handling is missing.

**Fix:** Guard `if (members.isEmpty) return _conversation.contact.name;`.

---

### [BUG] `chat_repository.dart` — `_conversations` is a static mutable list; mutations leak across instances and test runs

**Location:** `static final List<ChatConversation> _conversations = […]`.

Messages appended inside `ChatThreadScreen` mutate this shared static list. Any subsequent construction of `InMemoryChatRepository` (e.g., after a provider reset or in tests) sees the already-mutated state from the previous session. This silently corrupts the seed data.

**Fix:** Move `_conversations` and `_roster` to instance fields, copying the seeds in the constructor.

---

### [RISK] `chat_thread_screen.dart` — duplicate message ID on sub-millisecond double-send

**Location:** `_sendMessage()`, `id: 'msg-sent-${DateTime.now().millisecondsSinceEpoch}'`.

If `TextField.onSubmitted` and `_SendButton.onTap` fire in the same event flush (e.g., hardware keyboard Enter + simultaneous button tap), both calls read non-empty text before `_inputController.clear()` inside `setState` executes for the first call. Two messages with identical millisecond-based IDs are inserted. If IDs are used as widget `Key` values anywhere downstream, Flutter will throw a duplicate-key error.

**Fix:** Use a monotonic counter (`_msgSeq++`) or `UniqueKey()` for outgoing IDs.

---

### [RISK] `chat_thread_screen.dart` — `_scheduleAutoReply` cancels pending reply; rapid-send swallows auto-replies

**Location:** `_scheduleAutoReply()` → `_replyTimer?.cancel()`.

Sending N messages within 1.6 s cancels all but the last timer. Only one auto-reply is generated regardless of how many messages were sent. Combined with `_markMyMessagesRead` being called only on that single reply, several outgoing messages remain permanently stuck in `MessageStatus.sent` (single-tick) even after the contact "responds".

**Fix:** Acceptable trade-off for a demo, but document it. Alternatively queue one reply per send.

---

### [EDGE] `chat_thread_screen.dart` — very long unbreakable token overflows bubble

**Location:** `_BubbleBody.build`, `Text(message.text, …)` with no `overflow` or `maxLines`.

A message containing a URL or a long run of characters without whitespace (e.g. `"https://…/very-long-path"`) that exceeds `maxWidth: screenWidth * 0.72` will visually overflow the bubble container because `Text` soft-wraps on Unicode line-break opportunities only. The result is painted outside the rounded `Container`, clipping or overflowing into adjacent bubbles.

**Fix:** Add `overflow: TextOverflow.clip` (or `.ellipsis`) and consider `SelectableText` for copy-ability.

---

### [EDGE] `chat_thread_screen.dart` — RTL/Arabic text renders left-aligned in bubble

**Location:** `_BubbleBody.build`, `Text(message.text, …)` and `_MessageInputRow`, `TextField(…)`.

Neither widget sets `textDirection` or `textAlign`. Flutter's default paragraph direction is LTR. A message typed in Arabic or Hebrew renders individual characters in the correct Unicode bidi order but the paragraph aligns from the left edge of the bubble instead of the right. The input field has the same issue.

**Fix:** `Text(…, textDirection: TextDirection.rtl)` conditionally, or use `Directionality` wrapping based on locale.

---

### [EDGE] `chat_repository.dart` — empty roster returns full list because ID ranges don't overlap

**Location:** `availableContacts()`, `inThread` set vs `_roster` IDs.

Seeded conversation contacts use `'off-101..106'`; roster uses `'off-201..206'`. The `inThread.contains(contact.id)` check never matches, so **all six roster members are always available** and the deduplication path is never exercised. Starting a new conversation with a roster member and then re-opening the "new chat" picker correctly removes them (the dynamic path works), but the static seed never validates the filter logic.

**Fix:** Align roster IDs with seeded conversation contacts, or acknowledge this is intentional seed design.

---

### [EDGE] `chat_repository.dart` — messaging yourself not prevented

**Location:** `startConversation`, `availableContacts`.

There is no concept of "the current user's own ID" in the repository. If the logged-in officer's own `ChatContact` were ever added to `_roster` (e.g., during roster population from a real API), the UI would allow them to open a conversation with themselves. The auto-reply simulation would then impersonate them with canned phrases.

**Fix:** Inject the current user's ID and filter it from `availableContacts`.

---

### [NIT] `chat_thread_screen.dart` — `_nextReplier` and `_nextReply` use inconsistent counters

**Location:** `_scheduleAutoReply` — `replier` is captured at schedule time; `_nextReply()` is evaluated at timer-fire time.

After rapid sends, the typing indicator shows the name captured for the *last* send but the reply text cycles based on the *current* inbound-message count at fire time. These can drift visually (e.g., "Marlon Stewart is typing…" but the reply cycles to Keisha's slot).

**Fix:** Capture `_nextReply()` alongside `_nextReplier()` at schedule time.

**TOP ISSUE:** `startGroupConversation` crashes with `StateError` on any empty-members call — unchecked `members.first` is a guaranteed runtime exception with zero recovery path.

## Worker 11 — presence

## Presence / Last-Seen Audit — `lib/screens/chat/chat_presence.dart`

### Findings

**[BUG] `_placeholder()` — `int.minValue.abs()` overflows, producing a negative list index**

```dart
// line ~107
final gradient = _avatarGradients[initials.hashCode.abs() % _avatarGradients.length];
```

`String.hashCode` can return `dart:core`'s minimum 64-bit signed integer (`-9223372036854775808`). In Dart, `.abs()` on that value overflows and returns the same negative number. `negativeInt % 5` in Dart returns a negative remainder (e.g. `-3`), causing a `RangeError` (index out of range) at runtime when the avatar tries to paint.

Fix: `initials.hashCode.abs() % …` → `initials.hashCode.remainder(_avatarGradients.length).abs()`, or clamp with `(initials.hashCode % _avatarGradients.length + _avatarGradients.length) % _avatarGradients.length`.

---

**[EDGE] `_relativeFromNow` — future-dated `lastSeen` silently returns `'just now'`**

```dart
// line ~23
final diff = DateTime.now().difference(moment);
if (diff.inMinutes < 1) return 'just now';
```

When `moment` is ahead of `DateTime.now()` (device clock skew, or a `lastSeen` accidentally stamped with a future time), `diff` is negative. `diff.inMinutes < 1` is true for *any* negative duration, so any future timestamp — including one days ahead — renders as `'last seen just now'`. For officers relying on recency data this is a silent correctness failure.

Fix: add `if (diff.isNegative) return 'just now';` as the very first guard so the intent is explicit, and consider logging a warning for skews beyond ~60 s.

---

**[RISK] `DateTime.now()` (local) vs potentially UTC `lastSeen` — parse-time ambiguity**

```dart
// line ~22
final diff = DateTime.now().difference(moment);
```

`DateTime.difference()` operates on `millisecondsSinceEpoch`, so local vs UTC arithmetic is correct *as long as both values carry their timezone flag*. The risk surfaces at deserialization: `DateTime.parse("2026-06-08T10:00:00")` (no `Z`) produces a local `DateTime`, while `DateTime.parse("2026-06-08T10:00:00Z")` produces UTC. In this in-memory system `lastSeen` is presumably set via `DateTime.now()` (local), but if any path uses `.toUtc()` or parses a bare ISO string, the flag mismatch can add hours of drift near DST boundaries.

Fix: enforce `lastSeen` is always `DateTime` local (never `.toUtc()`) at the point of assignment, or compare `moment.toLocal()` explicitly in `_relativeFromNow`.

### `chat_repository.dart`

**[BUG] `_groupSequence` is instance-scoped; `_conversations` is static**
`InMemoryChatRepository._groupSequence` resets to `0` each time a new repository instance is created (e.g., after the chat list screen is popped and pushed again), but `_conversations` persists across instances. The next group created after recreation will receive `grp-new-1` — a duplicate of one that already exists in the shared list.
*Fix:* Make `_groupSequence` `static` alongside `_conversations`, or derive IDs from `_conversations.length`.

**[EDGE] `startGroupConversation` — `members.first` throws if `members` is empty (~line 70)**
No guard before accessing `members.first` as the group conversation's `contact`. An empty list causes a `RangeError` at runtime.
*Fix:* Add `assert(members.isNotEmpty, 'A group must have at least one member')` or validate at call site.

**[NIT] `startConversation` iterates `_conversations` twice (~line 58)**
`.where(...).isNotEmpty` followed by `.where(...).first` traverses the list twice. Use `firstWhereOrNull` from `package:collection`.

### `chat_thread_screen.dart`

**[RISK] `_markMyMessagesRead` reconstructs `ChatMessage` by enumerating all fields (~line 160)**
Copies every field individually to flip `status`. If `ChatMessage` ever gains a new field, this method silently drops it. This is a fragile copy-by-enumeration pattern.
*Fix:* Add `copyWith({MessageStatus? status})` to `ChatMessage` and call `message.copyWith(status: MessageStatus.read)`.

**[EDGE] `_nextReplier` capture vs `_nextReply` evaluation are not in the same moment (~lines 115–125)**
`replier` is captured at `_scheduleAutoReply` call time, but `_nextReply()` runs inside the `Timer` callback 1600 ms later. If the user fires messages rapidly (each cancel-and-reschedule), the typing-indicator name and the actual canned reply index can diverge.

Two separate `.where((m) => !m.fromMe).length` traversals for the same value.

## Chat Feature QA — End-to-End Flow Review

### [BUG] `chat_thread_screen.dart` — thread opens at the top, not the latest message

`_scrollToBottom()` is only called after `_sendMessage` and after the auto-reply timer fires. There is no `initState` (or `addPostFrameCallback`) call to scroll on first render. Every thread that has existing messages opens showing the oldest message.

**Fix:** Add to `_ChatThreadScreenState.initState`:
```dart
WidgetsBinding.instance.addPostFrameCallback((_) => _scrollToBottom());
```

---

### [BUG] `new_group_screen.dart:48` — group member picker silently hides 1:1 contacts

`_loadContacts` calls `availableContacts()`, which is explicitly documented as returning officers *"not already in a one-to-one thread."* The moment a user starts a 1:1 with, say, Marlon Stewart (`off-201`), he vanishes from the group member picker permanently. The seeded IDs (`off-101`–`off-106`) and roster IDs (`off-201`–`off-206`) don't overlap so this is invisible in the demo, but it fires the instant any roster officer gets a 1:1 thread.

**Fix:** Add `Future<List<ChatContact>> allContacts()` to the repository (returns `_roster` directly) and call that in `NewGroupScreen._loadContacts` instead.

---

### [RISK] `chat_repository.dart` — `_groupSequence` (instance) vs `_conversations` (static) lifetime mismatch

`_conversations` is `static final` and lives for the process lifetime. `_groupSequence` is an instance variable that resets to `0` when a new `InMemoryChatRepository` is constructed. If the widget tree is torn down and rebuilt (hot restart, re-entry into the chat section after it leaves the tree), the new instance starts numbering groups at `grp-new-1` again while `_conversations` already contains a `grp-new-1`. Duplicate IDs break any lookup or dedup logic added later.

**Fix:** Make `_groupSequence` `static` to match the lifetime of `_conversations`, or make `_conversations` non-static and inject it via constructor so instance and list share the same scope.

---

### [EDGE] `chat_list_screen.dart:85` — list ordering never updates after a message is sent

`_openThread` calls `setState(() {})` when returning from a thread. This redraws the tile with the new last-message preview (because `_conversations` holds the same list reference), but the conversation stays in its current slot. Active threads don't bubble to the top.

**Fix:** Call `_loadConversations()` (or sort `_conversations` by `lastMessage.sentAt` descending) inside the `setState` after `Navigator.push` returns in `_openThread`.

---

### [NIT] `chat_thread_screen.dart` / `chat_list_screen.dart` — `_formatTime` duplicated

Identical `_formatTime(DateTime)` implementations exist in both `_ConversationTile` and `_BubbleFooter`. Zero risk, but violates DRY — extract to a top-level helper in `chat_style.dart` or a dedicated `chat_utils.dart`.
